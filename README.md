Цели `make` (`make` или `make help` выводит список):

- `make start` — создаёт `.env` и `secrets/`, если их нет, собирает и запускает стек; данные БД сохраняются, повторный запуск ничего не удаляет.
- `make stop`, `make restart` — остановка и перезапуск контейнеров. `make restart` = `stop`, затем те же контейнеры поднимаются по цепочке зависимостей (`up -d --no-recreate --wait`: db → migrate → audit_prepare → seed → api → proxy) с проверками `make start`, но без пересборки; режим туннеля `make ngrok` сохраняется. Если сервис не стал running/healthy (например, `audit_anchor` красный), restart завершается с ошибкой.
- `make clean` — удаляет контейнеры и сети Compose (`down`), данные БД сохраняются.
- `make logs`, `make ps` — логи всех сервисов (`logs -f`) и список контейнеров.
- `make test` — тесты против запущенного стека; адреса и проект меняются переменными `TEST_BASE` (по умолчанию `https://localhost:8450`), `TEST_MAILPIT` (`http://127.0.0.1:8025`), `TEST_PROJECT`, а также `PYTHON` и `PYTEST_ARGS`.

**`make reset` и `make fclean` удаляют БД.** `reset` выполняет `down -v` и затем `start`; `fclean` выполняет `down -v --rmi local --remove-orphans` только для этого Compose-проекта (`docker system prune` не вызывается). Обе цели сначала спрашивают подтверждение; `CONFIRM=yes` пропускает вопрос, без `yes` ничего не удаляется.

Все цели вызывают `$(COMPOSE)` (по умолчанию `docker compose`), поэтому другой проект можно указать так: `make start COMPOSE="docker compose -p planera"`.



FastAPI, PostgreSQL и Nginx.

API и `seed` подключаются к PostgreSQL ролью `clinic_api`; `POSTGRES_USER` используется только миграциями и администрированием. Одноразовый сервис `migrate` применяет схему, роли и RLS-политики до запуска API. Роли `app_guest`, `app_patient`, `app_doctor`, `app_registrar` и `app_admin` используются как контексты доступа.

Схему и RLS применяет `migrate` от имени владельца БД; сид использует `clinic_api` и ролевые контексты. При первом запуске фиксированный seed-администратор создаётся ограниченной `SECURITY DEFINER`-функцией, доступной только `clinic_api` и работающей лишь при пустой таблице `users`. Остальные демо-учётки создаёт такая же функция, но только для заранее заданных email; `clinic_api` не получает `INSERT` в `users`. Для защищённых запросов `db_as(user)` в транзакции задаёт `SET LOCAL ROLE app_*` (роль выбирается только из белого списка) и `app.user_id`. RLS защищает клинические таблицы `appointments`, `visit_notes` и `prescriptions`, а также ограничивает доступ врача к своим `slots`, `work_hours`, `time_off`, `holidays` и заявкам time off. Врач получает данные пациентов только через ограниченную функцию `doctor_patients()`, а не прямым чтением `users`; она включает пациентов со `scheduled` и `completed` записями за последние 12 месяцев. Для подписей в расписании и календаре используется отдельная `doctor_visit_patients()`, которая учитывает и `cancelled`, поэтому отменённые визиты остаются в расписании врача.

`clinic_api` может читать из `users` только несекретные колонки; прямое чтение `password_hash` запрещено. Вход проверяется функцией `SECURITY DEFINER`, которая сверяет пароль в PostgreSQL и возвращает только данные учётной записи. Версия `auth_version` хранится в подписанной сессии и в `users`; её увеличение после смены или сброса пароля аннулирует все старые сессии пользователя. Пароль, который задаёт сам пользователь, везде одинаковый: 8–72 символа, минимум 4 разных, буква и цифра, не email и не его локальная часть, не из короткого списка вроде `password` и `12345678`. Пробелы внутри пароля разрешены, по краям — нет, и пароль не обрезается молча. Email перед сохранением, входом, сбросом и поиском приводится к `strip()` + `lower()`; пробелы внутри адреса запрещены. При смене или сбросе уже существующего пароля новый не может совпасть со старым хешем. После смены уходит письмо без пароля и без ссылки.
Неудачный вход ограничен пятью попытками на пару «email + источник» за 15 минут и 100 попытками с одного источника за 15 минут; при превышении возвращается HTTP 429 с `Retry-After`. Источник передаётся доверенным reverse proxy, а в таблице попыток хранятся только хеши email и источника. Под Docker Desktop все клиенты видны как шлюз Docker, поэтому лимиты на источник фактически общие для всех (как у входа); на сервере за reverse proxy источник — настоящий адрес клиента. Для существующего и несуществующего email выполняется одна проверка `crypt()` с одинаковой стоимостью, чтобы время ответа не показывало, есть ли учётка. Заблокированная учётка при входе без сессии отвечает так же, как неверный пароль: HTTP 401 «Invalid email or password», попытка засчитывается в тот же лимит; «Account is blocked» показывается только тому, у кого уже была сессия, отозванная блокировкой. NUL-байты во вводимых текстах отклоняются до обращения к PostgreSQL.

`appointments.status` ограничен значениями `scheduled` и `cancelled`. RLS разрешает пациенту создавать запись только на свободный существующий слот и менять статус только с `scheduled` на `cancelled`; заблокированный пациент не проходит проверку. Проверка занятости слота не раскрывает пациенту чужие строки appointments.

Время слотов хранится как местное время клиники; база данных, API и соединения PostgreSQL настроены на `Asia/Yerevan`. Врач видит заметки и рецепты по своим `scheduled` и `cancelled` записям, но добавлять их можно только для `scheduled`. Каждая заметка и каждый рецепт хранятся отдельной строкой; текст ограничен 4000 символами на сервере (до шифрования), а в базе хранится только в зашифрованном виде. Пациент видит свои записи на `/my/records`, в том числе после отмены визита. `/admin/audit` показывает последние события бронирования, медицинских записей и административных изменений; журнал хранит только актёра, действие и идентификатор цели, но не текст заметок или рецептов.

Врач может открыть список своих пациентов на `/doctor/patients` и карточку пациента с историей визитов, заметками и рецептами. Список и карточка ограничены функцией `doctor_patients()` и политиками RLS; медицинские записи отображаются только в пределах действующих правил доступа.

Регистратор может просматривать все визиты выбранного дня и всей недели для всех врачей на `/registrar/appointments?day=YYYY-MM-DD&view=week`; фильтр `doctor_id=ID` ограничивает календарь выбранным врачом. Справочник `/registrar/patients` показывает имя, телефон, email, статус блокировки и количество будущих визитов, ищет по имени или email, и регистратор может исправить имя и телефон пациента; поиск на странице слотов выполняется через `/registrar/patients/search`. Регистратор не получает медицинские тексты, пароли или другие медицинские данные. Медицинские тексты и настройки графика регистратору недоступны. Врач видит только свой календарь на `/doctor/calendar?day=YYYY-MM-DD`: свободные слоты, занятые визиты и закрытия по выходным, отпуску или празднику, без действий бронирования или редактирования расписания. Отменённая запись больше не занимает слот календаря. Для обоих календарей доступны режимы `view=day|week`, навигация по дню или неделе и переход к сегодняшней дате. Неверные параметры даты и режима показывают сообщение и безопасно переключают календарь на текущий день. Врач может отправить запрос time off с датами и комментарием; только администратор может одобрить или отклонить его. Одобрение создаёт обычный период `time_off` и удаляет свободные слоты; существующие визиты остаются для ручной отмены администратором.

Администратор видит будущие записи на `/admin/schedule` и может отменить каждую по отдельности. Генерация слотов и отпуск на прошедшие даты отклоняются; диапазон генерации ограничен 90 календарными днями включительно. Регистратор не может отменять прошедшие визиты.

Фильтры и страницы (только GET, значения проверяются по белым спискам и строгим разбором, неверное значение игнорируется с предупреждением, без 500). `/doctors` — специальность и поиск по имени врача (`specialty`, `q`, до 100 символов, `ILIKE` с экранированием `%` и `_`). Слоты врача — окно дат `day=YYYY-MM-DD` и `view=week|day` (по умолчанию неделя с сегодняшнего дня; прошедшие слоты регистратор и админ видят, только выбрав прошедшую дату), у регистратора ещё `hide_taken=1`. `/my` — `status=upcoming|past|cancelled|all` (по умолчанию `upcoming`), `doctor_id` из врачей своих визитов, `from`/`to` (не больше 366 дней), по 20 на странице (`page` до 500); заметки и рецепты грузятся только для визитов страницы и с фильтром по пациенту. Календарь регистратора — ещё `status=all|active` и `service_id`, у будущих визитов кнопки Reschedule и Cancel. `/doctor/appointments` — `status` и страницы по 20. Журнал `/admin/audit` (только admin) — `action` (точное значение или группа вида `auth.`), `actor_role`, `actor` (точный email, без поиска по подстроке), `target_type`, `target_id` (находит и старый id перенесённого визита), `from`/`to`; страницы по 50 по ключу `before_id` («Next» и «Newest»), без OFFSET. Каждый просмотр журнала сам пишется в журнал как `audit.view` (только какие фильтры заданы, без их значений; подробнее — раздел «Журнал аудита» ниже).

Перенос записи: `/appointments/{id}/reschedule` — пациент для своей будущей `scheduled` записи, регистратор для любой будущей записи незаблокированного пациента; врач и админ не переносят (админ только отменяет). Новый слот — только тот же врач и та же услуга, будущий, свободный, не выходной и не отпуск; другой врач или услуга — через отмену и новую бронь. Запись с заметками или рецептами не переносится (`has_records`). Всё в одной транзакции под ролью пользователя: старый визит отменяется, затем проверяется и вставляется новый (RLS INSERT и `is_valid_free_slot` как при брони, новых грантов на `appointments` нет — `UPDATE` только `status`), затем DEFINER `record_appointment_reschedule` ещё раз сверяет пару и пишет одно событие `appointment.reschedule` (`target_id` и `new_value` — новый id, `old_value` — старый, без имён и email); любая ошибка откатывает всё. Письмо «Appointment rescheduled» пациенту и врачу уходит после COMMIT. CHECK `audit_events_change_values_check` на старом томе один раз пересоздаётся при старте `migrate`. Пациент — не больше 3 переносов за 24 часа (регистратор не ограничен); событие журнала пишется только в той же транзакции, что и сам перенос, и не больше одного на визит.

Гость может создать аккаунт только с ролью `patient` на `/register`. Email нормализуется к нижнему регистру и уникален без учёта регистра; пароль короче 8 символов после обрезки пробелов, из одного повторяющегося символа, совпадающий с email или его локальной частью, либо входящий в список типовых значений, отклоняется без создания пользователя. При регистрации обязательны полное имя (2–100 символов, без управляющих) и телефон (цифры, пробелы, `+()-`, минимум 5 цифр, до 40 символов). Учётку и профиль создаёт одна `SECURITY DEFINER`-функция `register_patient` (роль `patient` зашита в функции, данные проверяются ещё раз); у гостевой роли нет `INSERT` в `users`. Регистрация не создаёт сессию. Новый пациент получает письмо со ссылкой подтверждения (действует 24 часа, одноразовая); ссылка открывает `/verify-email` без email на странице, подтверждение — кнопкой (POST с CSRF), после него вход через `/login`. До подтверждения вход не проходит и отвечает так же, как неверный пароль (см. ниже «Один ответ на неудачный вход»). Новую ссылку можно запросить с `/login` (форма есть на странице всегда): ответ всегда один и тот же, письмо уходит только неподтверждённому пациенту, старые ссылки гаснут, лимиты — 5 запросов за 15 минут на email и IP, 100 на IP, 10 в сутки на email. Сброс пароля по «Forgot password?» доступен и неподтверждённой учётке и подтверждает почту, а старые сессии и пароль перестают действовать; так настоящий владелец адреса забирает учётку, созданную чужими руками. Служебные учётки подтверждаются ссылкой установки пароля. Демо-учётки создаются уже подтверждёнными; на стенде письма смотрите в Mailpit. Создание служебных ролей остаётся вне публичной формы. Регистрация ограничена: 20 попыток за 15 минут и 100 в сутки с одного источника, 5 в сутки на email; при превышении HTTP 429 с `Retry-After`, ответ одинаков для существующего и нового email; в таблице только хеши. При сбое базы — 503, регистрация без лимита не проходит.

Имя и телефон пациента хранятся в `patient_profiles` (CHECK в базе, `FORCE ROW LEVEL SECURITY`). Пациент видит и правит только свой профиль на `/me`, регистратор — профили пациентов, администратор видит только имя (без телефона), врач — имя и телефон только своих пациентов через `SECURITY DEFINER`-функцию `doctor_visit_patients` (то же правило, что для email: визиты за 12 месяцев, включая отменённые); гость профилей не видит. В календарях и списках имя показывается первым, email — вторым. Правка пишется в аудит как `patient.profile.update` только с id, без имени и телефона. Демо-пациенты: `pat@clinic.local` — Narek Hakobyan, `pat2@clinic.local` — Ani Sargsyan; у пациентов, созданных до этой таблицы, стоит заглушка, и `/me` просит её заменить. Кабинет пациента `/me` показывает до трёх ближайших будущих визитов только этого пациента и даёт ссылки на полную историю `/my` и медицинские записи `/my/records`. На странице врача пациент выбирает активную услугу до выбора слота и видит длительность услуги и буфер. После записи `/my` подтверждает врача, дату, время и услугу; список визитов показывает ближайшие будущие записи первыми, длительность, статус и кнопку отмены с подтверждением. Регистратору также показываются детали успешной записи. Любая роль может сменить собственный пароль, указав текущий; сервер применяет те же ограничения, что и регистрация, включая пароль, совпадающий с email. Проверка и обновление выполняются `SECURITY DEFINER`-функцией с учётом роли и `auth_version`, без права приложения менять `users.password_hash` напрямую. Смена фиксируется в аудите без записи пароля или его хеша.

Подтверждения действий. Перед записью, отменой и переносом браузер спрашивает подтверждение с врачом, услугой, датой и временем визита (у регистратора и администратора — ещё с именем пациента). Это удобство интерфейса (`data-confirm` + `app.js`, текст экранируется Jinja), а не контроль безопасности: без JavaScript форма уходит без вопроса, защиту дают CSRF, RLS и проверки на сервере.

Регистрация на занятый email. `/register` отвечает одинаково для нового и уже занятого адреса (любой регистр, пробелы по краям): 303 на `/login?registered=1` с текстом «Check your email for the next step…». Новый адрес получает ссылку подтверждения, владелец занятого — письмо «Your clinic account» без токена и без имени, со ссылками на вход и «Forgot password?»; учётка, пароль и токены при этом не меняются. Неподтверждённую учётку, созданную чужими руками, владелец адреса забирает сбросом пароля. Сбой SMTP одинаков для обеих веток (`mail=failed`), в лог пишется одна строка `could not send registration email (<класс ошибки>)` без стека и адреса.

Один ответ на неудачный вход. Неизвестный email, неверный пароль, заблокированная учётка и неподтверждённая учётка с верным паролем получают одинаковый ответ 401 «Invalid email or password. If you have just registered, confirm your email first.»; каждая такая попытка считается в лимите входа, счётчик не сбрасывается. Причина остаётся только в журнале (`auth.login.failure`: `blocked`, `unverified` или `bad_credentials`, без email).

Дедлайн для пациента. Пациент может отменить или перенести визит онлайн не позже чем за N часов до начала: настройка администратора на `/admin/settings` (0–48, по умолчанию 2; 0 — до начала), меняется только функцией `set_patient_change_deadline_hours` с записью `clinic.change_deadline.update` (старое и новое значение). Граница считается в `public.patient_change_cutoff()` по времени `Asia/Yerevan` и проверяется в RLS-политике `appointments_patient_update`, поэтому `SET TimeZone` её не сдвигает, а прямой UPDATE внутри дедлайна меняет 0 строк. На `/my` вместо кнопок — «Online changes closed…», попытка отменить или перенести даёт `too_late` с просьбой позвонить в клинику. Регистратор и администратор дедлайном не ограничены (визит только должен быть ещё не начат). Новый слот при переносе может быть и внутри дедлайна.

Страница ошибки. Непредвиденная ошибка в `api` даёт страницу 500 «Something went wrong» с коротким кодом `ref` (8 hex) и без деталей; та же строка `unexpected error ref=<код>` с методом, путём (без query) и классом исключения и стек — в `docker compose logs api`, по коду её легко найти. Если `api` недоступен, nginx отдаёт свою страницу 502/504 (`docker/proxy/errors/clinic-unavailable.html`) с теми же заголовками безопасности.

Администратор управляет врачами на `/admin/doctors`: может создать врача с учётной записью, изменить имя/специальность/стаж или деактивировать и повторно активировать врача. Перед деактивацией показывается число будущих визитов; они остаются запланированными и требуют отдельного решения. Администратор может блокировать другого администратора, но не собственную учётную запись. Администратор не задаёт пароль и не меняет email. Новый администратор создаётся только после подтверждения паролем текущего администратора; отказ пишется в аудит как `admin.create_denied`, успех — как `admin.create` с автором. Новые регистраторы, администраторы и врачи получают ссылку для установки пароля; существующие учётные записи — только «Send reset link» или «Forgot password?». Себе ссылку отправить нельзя. Последний оставшийся администратор не получает ссылку через сайт; на сервере это делает `docker compose exec api python send_reset_link.py admin@clinic.local`. Смена email доступна только владельцу и требует подтверждения и старого, и нового адреса. Ссылка действует 15 минут, уходит только по SMTP и не показывается в браузере. Access-лог API и прокси для `/reset-password` и `/confirm-email` не сохраняет `token`; `send_reset_link.py` при сбое SMTP печатает только `user_id`, не ссылку. `auth_version` аннулирует старые сессии. Медицинский текст закрыт `FORCE ROW LEVEL SECURITY`: у `app_admin` нет прав и политики на `visit_notes` и `prescriptions`. Ключ сессии читается из Docker secret `secrets/session_secret` и не может быть дефолтным. Локально письма принимает Mailpit на http://127.0.0.1:8025. После успешной записи и после отмены письмо уходит пациенту и врачу, если у адресата включены почтовые уведомления в `/me`: врач, услуга и время берутся из слота, без медицинского текста и номера записи. Письма о пароле и смене email отправляются всегда. Сбой SMTP не отменяет уже созданную или уже отменённую запись. Для настоящего сервера задайте `SMTP_HOST`, порт, `SMTP_STARTTLS` или `SMTP_SSL`, при необходимости логин (`SMTP_USERNAME`) и пароль в `secrets/smtp_password`, а также `PUBLIC_BASE_URL`. Публичная форма по-прежнему создаёт только пациентов. Адрес и телефон клиники на главной странице изменяются в `/admin/settings`. Значения по умолчанию «Educational stand» и «000-00-00» — демо-данные учебного стенда, а не реальные контакты; замените их в `/admin/settings` перед реальным использованием.

Услуги управляются администратором на `/admin/services`: у каждой услуги задаются длительность и буфер после неё, а также список врачей, которые её оказывают. Пациент или регистратор выбирает услугу на странице слотов соответствующего врача. В слотах сохраняются снимки длительности и буфера: визит пациента длится только `duration_minutes`, а врач резервируется на `duration_minutes + buffer_minutes`; буфер не мешает записи пациента к другому врачу. Изменение услуги влияет только на новые слоты, существующие слоты и записи сохраняют прежние интервалы. Нельзя снять с услуги врача с будущими записями: сначала нужно отменить эти визиты или оставить врача привязанным. Использованную услугу нельзя удалить — её можно деактивировать.

Для повторения проверки «сломанный SELECT» без фильтра по пользователю запустите `./tests/run_tests.sh tests/test_rls_boundary.py`: тест проверяет `SELECT id, patient_user_id` для appointments, visit_notes и prescriptions под пациентом, границы видимости врача, запрет регистраторам и администраторам читать `body`, а также запрет неадминистративным ролям читать аудит. Фактический вывод сохраняется в `experiments/rls_boundary_output.txt`.



Для первого запуска используйте `make start`; пересоздать окружение с пустой БД — `make reset`.

`.env` содержит только несекретные настройки. Пароли БД, ключ сессии и пароль SMTP лежат в `secrets/` (не коммитится) и попадают в контейнеры как Docker secrets в `/run/secrets/`. `scripts/init_secrets.sh` создаёт недостающие файлы, не перезаписывает существующие и удаляет из `.env` устаревшие строки `POSTGRES_PASSWORD`, `CLINIC_API_PASSWORD`, `SESSION_SECRET` и `SMTP_PASSWORD`. Если раньше пароли были в `.env`, после этого пересоздайте стек: `docker compose down -v && ./scripts/init_secrets.sh && docker compose up --build -d`. Подробнее: `docs/sec_doc.md`.

Права на файлы в `secrets/`: `600` для владельца плюс ACL на чтение только тому пользователю контейнера, который читает файл (`postgres_password` — uid 999, `clinic_api_password`, `session_secret`, `smtp_password`, `demo_password` — uid 10001; `audit_db_password` — uid 10002, пользователь `audit_anchor`; `migrate` работает от root и ACL не нужен). Fallback без `setfacl` или на ФС без ACL: если `init_secrets.sh` запущен от root, файл отдаётся этому uid (`chown`, права `400`); иначе файл остаётся `644` (кроме ключей медполей и `audit_anchor_key`: они остаются `600`), а скрипт печатает `warning` с командой `chmod 600 <файл> && sudo setfacl -m u:<uid>:r <файл>` (сначала `chmod`, потом `setfacl`, иначе ACL перестанет действовать). Файлы, которыми вы не владеете, скрипт не трогает (`note`). Ограничения: в rootless Docker uid контейнера отображается на subuid хоста, и ACL на `10001`/`999` не сработает; в Docker Desktop (macOS/Windows) права общих папок не применяются; `cp -r` и zip без сохранения ACL их теряют.

Внешний вид и заголовки безопасности. Интерфейс собран на Bootstrap 5.3.8 (только CSS, без Bootstrap JS и без CDN): `app/static/vendor/bootstrap/bootstrap.min.css` плюс свои `app/static/app.css`, `app/static/app.js` и SVG-иконки в `app/static/img/`. Статику отдаёт `api` (`StaticFiles`, без листинга каталогов); в шаблонах ссылки вида `/static/app.css?v=<хэш>`, поэтому такие URL кешируются надолго, а HTML-страницы отдаются с `Cache-Control: no-store`. В шаблонах нет `style=`, `on...=`, встроенных `<script>`/`<style>` и `data:`-картинок; подтверждения — атрибут `data-confirm`. nginx ставит строгий `Content-Security-Policy` (без `unsafe-inline`) и остальные заголовки на все ответы. Версия и SHA-256 Bootstrap, политика и правила — в `docs/sec_doc.md`, раздел 8.

Пароль демо-учёток (`admin`, `doc`, `doc2`, `pat`, `pat2`, `reg` @clinic.local) берётся только из `secrets/demo_password`: `seed` читает его как Docker secret и падает с ошибкой, если файла нет или он пуст. `init_secrets.sh` генерирует этот файл, если его нет, и не перезаписывает существующий, поэтому свой начальный пароль можно положить туда заранее. Известного демо-пароля в репозитории больше нет. Seed создаёт учётки только в пустой базе, поэтому в уже существующей базе остаётся старый демо-пароль, пока её не пересоздать: `docker compose down -v && ./scripts/init_secrets.sh && docker compose up --build -d`.

Текст заметок (`visit_notes.body`) и рецептов (`prescriptions.body`) шифруется в `api` (AES-256-GCM, библиотека `cryptography`) до записи в базу и расшифровывается только при показе врачу или пациенту. В базе и в дампе лежит пакет `fe2:<key_id>:<nonce>:<шифротекст>:<тег>`, а не текст; база принимает в этих колонках только такие пакеты. Пакет привязан к своей записи: в проверку целостности входят таблица, id строки и id визита, поэтому пакет, скопированный в другую строку (даже той же таблицы), не расшифровывается — `api` показывает ошибку, а не чужой текст. Ключ — файл `secrets/field_encryption_key` в формате `<key_id>:<64 hex>`; его создаёт `init_secrets.sh` (только если файла нет, существующий не перезаписывает и значение не печатает). Ключ монтируется как Docker secret только в `api`; `db`, `migrate` и `seed` его не получают, в SQL он не передаётся. Права на файл `600` плюс ACL на чтение для пользователя api (uid 10001), то есть не world-readable. Если `setfacl` нет, выполните `sudo chown 10001:10001 secrets/field_encryption_key secrets/field_encryption_previous_keys` (права `600` останутся). Без ключа или с пустым/битым ключом `api` не стартует.

Существующий том со старыми заметками открытым текстом шифруется при старте `api`: перед uvicorn выполняется `python -m migrate_medical_fields`, который шифрует открытые строки, перешифровывает пакеты первой версии `fe1` (без привязки к строке) в привязанные `fe2`, уже привязанные не трогает и безопасен при повторном запуске. Пока `api` с ключом не запускался на этом томе, старый текст остаётся открытым в дампе. Вручную: `docker compose exec api python -m migrate_medical_fields`.

Смена ключа без потери старых записей: `./scripts/rotate_field_key.sh` переносит текущий ключ в `secrets/field_encryption_previous_keys` (он остаётся для чтения) и создаёт новый с новым `key_id` (`v1` → `v2`). Затем `docker compose up -d --force-recreate api`: новые записи шифруются новым ключом, старые читаются по своему `key_id`. По желанию перешифровать старые строки новым ключом: `docker compose exec api python -m migrate_medical_fields --reencrypt`. Старый ключ удаляйте из `field_encryption_previous_keys` только после этого. Просто заменить `field_encryption_key` нельзя: всё, что записано старым ключом, перестанет читаться. Подробнее: `docs/sec_doc.md`.

### HTTPS на стенде (`CLINIC_TLS_MODE=local`)

`make start` (через `scripts/init_secrets.sh`) выпускает свой CA с `nameConstraints` (только `localhost`, `127.0.0.1`, `::1`; `extendedKeyUsage=serverAuth`) и серверный лист на год. Браузер предупреждает о сертификате, пока вы не импортируете `secrets/tls/ca.crt` (по желанию). Ключ CA не покидает хост и в контейнеры не попадает. Тесты ходят по HTTPS с `SSL_CERT_FILE=secrets/tls/ca.crt` (Makefile и `tests/run_tests.sh` ставят его сами).

**HSTS** на стенде — 1 час (`CLINIC_HSTS_MAX_AGE=3600`). HSTS действует на все порты `localhost`, поэтому после захода на стенд браузер будет открывать по HTTPS и другие локальные сервисы на `localhost`: Mailpit открывайте только по `http://127.0.0.1:<порт>`. Для настоящего домена — `31536000`; `includeSubDomains` и `preload` мы не ставим, это только рекомендация (preload практически необратим).

По умолчанию proxy слушает все интерфейсы (`0.0.0.0`), но сертификат стенда выпущен только на `localhost`/`127.0.0.1`/`::1`: с другой машины браузер предупредит о сертификате, а редирект с HTTP ведёт на `PUBLIC_BASE_URL` (`localhost`). Для доступа по сети используйте режим `provided` с настоящим именем. Чтобы открыть стенд только на этой машине, добавьте в `.env` строку `CLINIC_PROXY_BIND=127.0.0.1` и выполните `docker compose up -d proxy`.

Сессионная cookie: `SESSION_HTTPS_ONLY=true` по умолчанию (флаг `Secure`); `api` не стартует, если `PUBLIC_BASE_URL` не `https://`.

### Прод: `CLINIC_TLS_MODE=provided`

Образец настроек — `.env.prod.example`. Полная цепочка сертификата кладётся в `secrets/tls/server.crt`, ключ — в `secrets/tls/server.key`; `init_secrets.sh` их только проверяет, проверка вручную — `make tls-check`. В `PUBLIC_BASE_URL` — имя (не IP-литерал), без порта и пути. Получение сертификата: ACME DNS-01 (рекомендация) или HTTP-01 через webroot (`CLINIC_ACME_WEBROOT=true` и `docker-compose.acme.yml`). Обновление — только через `scripts/tls_reload.sh NEW_KEY NEW_FULLCHAIN` (проверка, бэкап, запись в те же inode bind-mount, `nginx -t`, graceful reload, сверка serial), например как `--deploy-hook` certbot: `--deploy-hook 'cd /srv/clinic && scripts/tls_reload.sh "$RENEWED_LINEAGE/privkey.pem" "$RENEWED_LINEAGE/fullchain.pem"'`. OCSP не нужен (Let's Encrypt закрыл OCSP в 2025), stapling — опция для корпоративного CA.

### Журнал аудита: хеш-цепочка и якоря

- Журнал `audit_events` только дописывается: `UPDATE`, `DELETE` и `TRUNCATE` запрещены триггерами, в том числе суперпользователю (триггеры в режиме `ENABLE ALWAYS`). Внешнего ключа на `users` нет: удаление неподтверждённого приглашения пишет событие `user.invite_discarded`, история остаётся.
- Каждая строка получает `seq`, `prev_hash` и `row_hash` = SHA-256 от предыдущего хеша и канонической формы строки v1 (поля по порядку, `<длина>:<байты>`, NULL — `-`, время — микросекунды UTC). Голова цепочки — `audit_chain_head`. Строки, записанные до `genesis_at`, получили хеши задним числом и не гарантированы. Пропала голова при наличии строк — `migrate` не стартует (восстановление из бэкапа), новую цепочку поверх старых строк он не строит.
- Сервис `audit_anchor` (пользователь БД `clinic_auditor`, только `SELECT` журнала и головы) раз в `CLINIC_AUDIT_ANCHOR_INTERVAL` секунд (по умолчанию 60, допустимо 10–3600) проверяет цепочку от последнего якоря и, только если она цела, дописывает в `audit_anchors/<chain_id>.log` якорь `seq` + хеш с HMAC-SHA256 (цепочка MAC по строкам). Ключ `secrets/audit_anchor_key` монтируется только в `audit_anchor`: права `600` + ACL на чтение uid 10002, либо от root `chown 10002` и `400`; если ни то, ни другое невозможно, ключ остаётся `600` с предупреждением (никогда не `644`) и `audit_anchor` не стартует, пока не получит доступ. Запись якорей и реестра идёт под `flock` на `audit_anchors/.lock`.
- Проверка: `make audit-verify` (`OK chain=… rows=… anchors=… last_anchor_age=…` или `BROKEN seq=… type=…`, код 1). `--strict` (`VERIFY_ARGS=--strict`) даёт код 3, если какая-то цепочка закрыта `forced` или `offline`. Код 2 и строка `ERROR cannot check: …` — «не проверено» (нет ключа или БД недоступна). Это тоже красный статус, а не «OK»: атакующий с доступом к БД (например, `REVOKE SELECT`) может превратить `BROKEN` (1) в 2.
- Полная проверка: `audit_anchor` при старте и затем раз в `CLINIC_AUDIT_FULL_CHECK_EVERY` секунд (по умолчанию 600, допустимо 60–86400) выполняет ту же проверку, что `make audit-verify` (вся цепочка от `seq` 1, реестр, триггеры), под тем же `flock` и в том же снимке БД, что и якорь. Так правка старых строк (до последнего якоря) видна не позже чем через 10 минут, без ручного `make audit-verify`. Результат цикл пишет в публичный файл статуса `/status/status.json` (том `audit_status`): только состояние `ok`/`broken`/`unchecked`, времена, `seq` и тип нарушения из белого списка, без путей, id цепочек, хешей и MAC. `--once`, `--retire` и `--health` этот файл не пишут; healthcheck `audit_anchor` не изменился.
- Плашка «Log integrity» — только на `/admin/audit` (только admin, ответ с `Cache-Control: no-store`). `api` читает `status.json` из того же тома только на чтение (`audit_status:/audit_status:ro`), строго по схеме, и сам решает цвет по своим `CLINIC_AUDIT_ANCHOR_INTERVAL` и `CLINIC_AUDIT_FULL_CHECK_EVERY` (из окружения `api`, не из файла):
  - **OK** (зелёная) — только если инкрементальная проверка цела, последняя полная проверка прошла, в реестре не было подмены цепочки, последняя проверка не старше `3·interval+60` с, полная — не старше `2·full_every+60` с, и ни одно время не в будущем больше чем на 60 с;
  - **BROKEN** (красная) — нарушение с его типом и `seq` (например `row_hash`, `chain_replaced`); после подмены цепочки (`switch` в реестре, в том числе после `make reset … RETIRE_FORCE=yes` без архивации якорей) плашка остаётся красной навсегда, как и `make audit-verify`;
  - **not checked** (серая) — нет файла, файл испорчен или не по схеме, время в будущем, статус устарел (`audit_anchor` остановлен или завис), нет БД, нет каталога якорей, цепочка закрыта.
  Плашка — **индикатор, а не источник истины**: она живёт на том же хосте и показывает то, что записал `audit_anchor`. Источник истины — `make audit-verify` и копии якорей за пределами сервера. Времена на плашке — Asia/Yerevan.
- Просмотр журнала пишется в журнал: каждый `GET /admin/audit` — событие `audit.view` (актёр — admin, цель `audit_log`, `target_id` — битовая маска заданных фильтров: 1 `action`, 2 `actor_role`, 4 `actor`, 8 `target_type`, 16 `target_id`, 32 `from`, 64 `to`; `before_id` в маску не входит). Значения фильтров (email, id, даты) и их хеши не пишутся никогда; на странице журнала маска показана списком имён полей. Повтор той же маски тем же admin пишется снова только через 10 минут после записанного события (окно — константа `public.audit_view_window()`, `api` её не меняет), новый набор фильтров пишется всегда. Запись идёт функцией `public.record_audit_view` (`SECURITY DEFINER`, `EXECUTE` только у `app_admin`) в отдельной транзакции до чтения журнала; если записать не удалось, журнал не показывается (**fail closed**, страница ошибки 503).
- На свежем стенде, пока `audit_anchor` не записал первый якорь (до одного интервала после `make start` или `make reset`), `make audit-verify` печатает `BROKEN type=registry_missing … no registry and no anchors yet`: реестра ещё нет. Это нормально; через интервал проверка даёт `OK`. Если же файлы якорей есть, а `chains.log` нет, `registry_missing` — настоящая тревога.
- Если каталога якорей нет (удалён или переименован) или он пуст, а в БД уже есть цепочка дальше genesis, `audit_anchor` при `make start`/`restart` не открывает новую цепочку молча: пишет `ERROR audit chain registry missing`, ничего не пишет в каталог, становится `unhealthy`, `make audit-verify` даёт `BROKEN type=registry_missing … the database holds chain=…` (rc 1). Выход — вернуть каталог или `make reset CONFIRM=yes RETIRE_FORCE=yes` (`forced no_registry@-`). На свежем стенде ложной тревоги нет: одноразовый `audit_prepare` пишет `open` до запуска `seed` и `api`.
- **Окно риска — до 60 с (один интервал):** правку журнала, сделанную суперпользователем БД после последнего якоря (отключить триггеры и пересчитать хеши), якорь не увидит, пока она не попадёт под следующий якорь — а следующий якорь уже не пишется, если цепочка не сходится с предыдущим. Правка строк до последнего якоря обнаруживается всегда (эксперимент E6: 20/20, `experiments/e6_report.md`). Окно можно сжать до 10 с через `CLINIC_AUDIT_ANCHOR_INTERVAL`. Честная модель угроз: суперпользователь БД может отключить триггеры и пересчитать цепочку — его ловят только якоря.
- Реестр цепочек `audit_anchors/chains.log` (`open`, `retire`, `switch`, тоже с HMAC): новая цепочка без закрытия старой — тревога `chain_replaced` (healthcheck красный, `verify_audit` — `BROKEN type=chain_replaced`). `make reset` и `make fclean` сначала останавливают `proxy` и `api` и закрывают цепочку (`anchor.py --retire`), поэтому плановый сброс тревоги не даёт. При сломанной цепочке сброс останавливается, ничего не удаляя, но `proxy` и `api` остаются остановленными — `make start` вернёт стенд. Том БД проверяется через `$(DOCKER) volume inspect`, где `DOCKER` — часть `COMPOSE` до слова `compose` (`sudo -n docker compose …` → `sudo -n docker`; можно задать `DOCKER=…` явно). Без проверки цепочки (`--retire --offline`) сброс идёт только если Docker ответил `no such volume`; любая другая ошибка (нет доступа к Docker, демон не запущен, sudo просит пароль) останавливает сброс, ничего не удаляя; осознанный сброс — `make reset CONFIRM=yes RETIRE_FORCE=yes` (в реестре `retire … forced`, `verify_audit` печатает `WARN`). После подмены цепочки (`chain_replaced`) `make reset`/`make fclean` тоже требуют `RETIRE_FORCE=yes CONFIRM=yes`: в реестре `retire … forced chain_replaced@-`, строка `switch` остаётся, и `verify_audit` по-прежнему даёт `BROKEN type=chain_replaced`. Если реестра нет (каталог якорей удалён, переименован или подменён), а в БД есть цепочка (`last_seq > 0`; на любом запущенном стенде это так — seed и события старта), сброс тоже отказывает (rc 2) без `RETIRE_FORCE=yes`; с ним в новом реестре остаётся `retire … forced no_registry@-`. Без тома БД (офлайн) закрывать нечего — сброс идёт как раньше.
- **Начать заново после расследования подмены** (только администратор хоста и только после разбора инцидента: снятых копий БД и якорей, выводов и решения): тревога `chain_replaced` в `verify_audit` держится, пока в реестре есть строка `switch`, и обычной командой не снимается — так задумано.
  1. Заархивируйте каталог якорей, не удаляя его: `mv audit_anchors audit_anchors-incident-$(date +%Y%m%d)` (или скопируйте на внешнее хранилище, например WORM, и затем переименуйте). Архив — улика, он нужен для `verify_audit --anchors <копия>` и разбора.
  2. `make reset CONFIRM=yes RETIRE_FORCE=yes`: каталога нет — make создаёт новый `audit_anchors/` с правами `700` + ACL (`scripts/anchor_dir.sh`, тот же код, что в `init_secrets.sh`). Реестра в нём нет, а в БД цепочка есть, поэтому без `RETIRE_FORCE=yes` reset откажет (rc 2, `BROKEN type=registry_missing`, ничего не удалено). С `RETIRE_FORCE=yes` первой строкой нового `chains.log` пишется `retire <chain> … forced no_registry@-` — видимый след того, что старую цепочку закрыли без её реестра; затем БД пересоздаётся.
  3. `audit_anchor` открывает новую цепочку; через интервал `make audit-verify` печатает `WARN retire forced chain=<старая> break=no_registry@-` и `OK chain=<новая> …` (rc 0; с `--strict` — rc 3, пока эта строка в реестре).
  Каталог якорей reset/fclean проверяет строго (`scripts/anchor_dir.sh --strict`): если он есть, но принадлежит другому пользователю (например, root с `755`, когда его создал Docker) или права не `700` + ACL `u:10002:rwx` без лишних записей, make останавливается до закрытия цепочки и ничего не удаляет; исправьте владельца (`sudo chown …`) и повторите.
  Без шага 1 `make reset … RETIRE_FORCE=yes` тоже пройдёт (в реестре `retire … forced chain_replaced@-`), но `verify_audit` останется красным — это и есть след инцидента.
- **Не выполняйте `git clean -fdx` (или `-X`) в рабочей копии:** `audit_anchors*/` в `.gitignore`, и такая очистка удалит якоря и реестр без следа. Каталог якорей создаёт `init_secrets.sh` (`700` + ACL `u:10002:rwx`); если `setfacl` нет, запустите `init_secrets.sh` от root. не открывайте его всем (права `777`): якоря и реестр сможет переписать любой пользователь хоста.
- Триггеры журнала — в режиме `ENABLE ALWAYS`. После ручного `DISABLE` включайте только `ALTER TABLE … ENABLE ALWAYS TRIGGER …` (простой `ENABLE` даёт режим `O`, `verify_audit` сообщит `trigger_mode`, а `migrate` вернёт `A`). **Восстановление только данных:** `pg_restore --data-only --disable-triggers …`, затем `ENABLE ALWAYS TRIGGER` — без `--disable-triggers` триггер `zz_audit_chain` перепишет `seq`, хеши и `created_at`, и история будет испорчена.
- На одном хосте root получает и БД, и ключ, и файлы якорей; против него помогают только якоря за пределами хоста. Рекомендация для прода: cron или systemd-timer раз в 5–15 минут копирует `audit_anchors/<chain_id>.log` и `chains.log` в WORM-хранилище (S3 Object Lock в режиме compliance, удалённый append-only syslog или почтовый ящик), а `verify_audit --anchors <копия>` сверяет внешнюю копию с локальной. Ключ `audit_anchor_key` храните и офлайн: без него якоря не проверить.
- **Прод: подтверждение reset и retire на двух машинах (только рекомендация, в стенде не реализовано).** `make reset … RETIRE_FORCE=yes` и `--retire` закрывают цепочку; в проде такое действие должно требовать подтверждения второго оператора с другой машины: подписанный им токен (ключ второго оператора не хранится на этом хосте) или одобрение в отдельном сервисе с собственным журналом. На одном хосте это не защита: root хоста подделает и запрос, и подтверждение, поэтому в стенде этого шага нет.

## Demo via ngrok

Публичное демо локального стенда через туннель ngrok (только `CLINIC_TLS_MODE=local`).

1. Установите ngrok и один раз сохраните свой authtoken: `ngrok config add-authtoken <token>`. Токен хранится в конфиге ngrok (или в `NGROK_AUTHTOKEN`), в репозитории и `.env` его нет, и скрипт его не печатает.
2. В `.env` укажите зарезервированный домен: `NGROK_DOMAIN=outspoken-wiry-fabric.ngrok-free.dev` (он уже есть в `.env.example`).
3. `make ngrok` проверяет ngrok, authtoken и домен, запускает `make start` с `PUBLIC_BASE_URL=https://$NGROK_DOMAIN` и `CLINIC_PUBLIC_TUNNEL=1` через окружение (`.env` не меняется) и открывает туннель на HTTPS-порт стенда (`CLINIC_PROXY_TLS_PORT`) с проверкой сертификата по `secrets/tls/ca.crt`. Ссылки в письмах и 308 с HTTP ведут на адрес туннеля.
4. Ctrl+C закрывает туннель, стенд продолжает работать со ссылками на туннель. `make ngrok-off` перезапускает стенд с адресом из `.env` (localhost).

Если Docker у вас работает только через `sudo`, обычный `sudo` сбрасывает `PUBLIC_BASE_URL` и `CLINIC_PUBLIC_TUNNEL`, и контейнеры остались бы на адресе из `.env`. Поэтому после `make start` скрипт сверяет адрес в контейнерах `api` и `proxy` с `https://$NGROK_DOMAIN` и при расхождении останавливается с ошибкой, не запуская ngrok. Запускайте Docker без `sudo` (группа `docker`) или сохраняйте окружение: `make ngrok COMPOSE="sudo -E docker compose"` (если sudoers запрещает `-E` — `sudo --preserve-env=PUBLIC_BASE_URL,CLINIC_PUBLIC_TUNNEL docker compose`).

При первом заходе ngrok показывает свою страницу-предупреждение, нажмите «Visit Site». За ngrok все посетители приходят с одного адреса, поэтому лимиты входа и регистрации по источнику общие для всех. Mailpit через туннель не открывается: открывайте его по `http://127.0.0.1:<порт Mailpit>`, не через `localhost` (на `localhost` браузер после HTTPS-стенда включает HSTS).

**Внимание:** пока туннель открыт, сайт доступен всем, у кого есть ссылка. Дополнительную защиту туннеля (пароль ngrok, OAuth, список IP) решено не ставить. Закрывайте туннель и выполняйте `make ngrok-off` сразу после демо.
