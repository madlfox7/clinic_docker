# Clinic Appointment Application

```bash
make start
```

Цели `make` (`make` или `make help` выводит список):

- `make start` — создаёт `.env` и `secrets/`, если их нет, собирает и запускает стек; данные БД сохраняются, повторный запуск ничего не удаляет.
- `make stop`, `make restart` — остановка и перезапуск контейнеров. `make restart` = `stop`, затем те же контейнеры поднимаются по цепочке зависимостей (`up -d --no-recreate --wait`: db → migrate → audit_prepare → seed → api → proxy) с проверками `make start`, но без пересборки; режим туннеля `make ngrok` сохраняется. Если сервис не стал running/healthy (например, `audit_anchor` красный), restart завершается с ошибкой.
- `make clean` — удаляет контейнеры и сети Compose (`down`), данные БД сохраняются.
- `make logs`, `make ps` — логи всех сервисов (`logs -f`) и список контейнеров.
- `make test` — тесты против запущенного стека; адреса и проект меняются переменными `TEST_BASE` (по умолчанию `https://localhost:8450`), `TEST_MAILPIT` (`http://127.0.0.1:8025`), `TEST_PROJECT`, а также `PYTHON` и `PYTEST_ARGS`.

**`make reset` и `make fclean` удаляют БД.** `reset` выполняет `down -v` и затем `start`; `fclean` выполняет `down -v --rmi local --remove-orphans` только для этого Compose-проекта (`docker system prune` не вызывается). Обе цели сначала спрашивают подтверждение; `CONFIRM=yes` пропускает вопрос, без `yes` ничего не удаляется.

Все цели вызывают `$(COMPOSE)` (по умолчанию `docker compose`), поэтому другой проект можно указать так: `make start COMPOSE="docker compose -p planera"`.

## Стек и модель доступа

Одноразовый `migrate` применяет схему, роли и RLS от владельца БД. API и `seed` подключаются как `clinic_api`; `POSTGRES_USER` нужен только для миграций и администрирования. Контексты: `app_guest`, `app_patient`, `app_doctor`, `app_registrar`, `app_admin`. Seed создаёт фиксированного администратора ограниченной `SECURITY DEFINER`-функцией только при пустой `users`, а другие демо-учётки — той же функцией только для заданных email; `clinic_api` не имеет `INSERT` в `users`. Защищённые запросы через `db_as(user)` задают в транзакции `SET LOCAL ROLE app_*` (только allowlist) и `app.user_id`. RLS защищает `appointments`, `visit_notes`, `prescriptions` и ограничивает врача своими `slots`, `work_hours`, `time_off`, `holidays` и заявками time off. Врач получает данные пациентов только через `doctor_patients()` (не читает `users` напрямую), для пациентов со `scheduled`/`completed` визитами за последние 12 месяцев; `doctor_visit_patients()` также включает отменённые визиты для подписей в расписании.

`clinic_api` читает из `users` только несекретные колонки; `password_hash` доступен только `SECURITY DEFINER`-проверке входа, которая сверяет пароль в PostgreSQL и возвращает данные учётной записи. Подписанный `auth_version` хранится в сессии и `users`; смена или сброс пароля аннулирует старые сессии. Пароль: 8–72 символа, минимум 4 разных, буква и цифра, не email и не его локальная часть, не типовой пароль вроде `password` или `12345678`. Внутренние пробелы разрешены, крайние — нет, молча пароль не обрезается; новый хеш при смене/сбросе не должен совпасть со старым. Email перед сохранением, входом, сбросом и поиском приводится к `strip()` + `lower()`, пробелы внутри запрещены. Письмо после смены не содержит пароль или ссылку.
Лимиты входа: 5 попыток на пару «email + источник» и 100 с одного источника за 15 минут; при превышении — HTTP 429 с `Retry-After`. Адрес источника берётся от доверенного reverse proxy, в таблице хранятся только хеши email и источника. В Docker Desktop все клиенты видны как шлюз Docker, поэтому лимит по источнику общий; на сервере за proxy виден адрес клиента. Для существующего и неизвестного email выполняется одна одинаковая по стоимости проверка `crypt()`, чтобы время ответа не раскрывало наличие учётки. NUL-байты отклоняются до обращения к PostgreSQL.

`appointments.status` ограничен значениями `scheduled` и `cancelled`. RLS разрешает пациенту создавать запись только на свободный существующий слот и менять статус только с `scheduled` на `cancelled`; заблокированный пациент не проходит проверку. Проверка занятости слота не раскрывает пациенту чужие строки appointments.

Время слотов — местное время клиники; БД, API и соединения PostgreSQL используют `Asia/Yerevan`. Врач видит заметки и рецепты своих `scheduled` и `cancelled` визитов, но добавляет их только к `scheduled`. Каждая запись хранится отдельной строкой; сервер ограничивает текст 4000 символами до шифрования, в БД он хранится зашифрованным. Пациент видит свои записи, включая отменённые, на `/my/records`. `/admin/audit` показывает последние события бронирования, медицинских записей и административных изменений; журнал содержит только актёра, действие и id цели, без текста заметок и рецептов.

На `/doctor/patients` врач видит своих пациентов и их историю визитов, заметки и рецепты; доступ ограничивают `doctor_patients()` и RLS.

Регистратор видит визиты всех врачей за день или неделю на `/registrar/appointments?day=YYYY-MM-DD&view=week`; `doctor_id=ID` фильтрует календарь. `/registrar/patients` показывает имя, телефон, email, статус блокировки и число будущих визитов, ищет по имени/email и позволяет править имя и телефон; поиск со страницы слотов — `/registrar/patients/search`. Регистратор не видит медицинские данные и не меняет график. Врач видит только свой календарь (`/doctor/calendar?day=YYYY-MM-DD`): свободные/занятые слоты и закрытия по выходным, отпуску или празднику, без бронирования и редактирования графика; отменённые визиты слот не занимают. Оба календаря поддерживают `view=day|week`, навигацию и переход к сегодня; неверная дата или режим показывают предупреждение и переключают на текущий день. Врач подаёт запрос time off с датами и комментарием; решает только администратор. Одобрение создаёт `time_off` и удаляет свободные слоты, но оставляет существующие визиты для ручной отмены администратором.

Администратор видит будущие записи на `/admin/schedule` и может отменить каждую по отдельности. Генерация слотов и отпуск на прошедшие даты отклоняются; диапазон генерации ограничен 90 календарными днями включительно. Регистратор не может отменять прошедшие визиты.

Параметры страниц принимаются только через GET и проверяются по белым спискам и строгому разбору; неверные значения игнорируются с предупреждением, без 500. `/doctors`: `specialty`, `q` (до 100 символов; `ILIKE` экранирует `%` и `_`). Слоты врача: `day=YYYY-MM-DD`, `view=week|day` (по умолчанию неделя от сегодня); прошедшие слоты регистратор и админ видят только при выборе прошедшей даты, у регистратора также `hide_taken=1`. `/my`: `status=upcoming|past|cancelled|all` (по умолчанию `upcoming`), свой `doctor_id`, `from`/`to` (максимум 366 дней), `page` (по 20, максимум 500); заметки и рецепты загружаются только для текущей страницы и с фильтром пациента. Календарь регистратора также принимает `status=all|active` и `service_id`; будущие визиты имеют кнопки Reschedule/Cancel. `/doctor/appointments`: `status`, по 20 записей. `/admin/audit` (только admin): `action` (точное значение или группа вроде `auth.`), `actor_role`, точный `actor` email, `target_type`, `target_id` (включая старый id перенесённого визита), `from`/`to`; по 50 записей через `before_id` («Next»/«Newest»), без OFFSET.

Перенос `/appointments/{id}/reschedule`: пациент — только свою будущую `scheduled` запись; регистратор — любую будущую запись незаблокированного пациента; врачу и админу запрещён (админ может отменить). Слот должен быть будущим, свободным, не в выходной/отпуске и у того же врача и услуги; для смены врача/услуги нужно отменить запись и создать новую. Визиты с заметками/рецептами (`has_records`) не переносятся. Операция атомарна: под ролью пользователя отменяется старый визит, проверяются RLS INSERT и `is_valid_free_slot`, создаётся новый (грант на `appointments` не расширяется: UPDATE только `status`); `record_appointment_reschedule` (DEFINER) сверяет пару и пишет одно событие `appointment.reschedule` в той же транзакции. В журнале `target_id`/`new_value` — новый id, `old_value` — старый, без имён/email; ошибка откатывает всё. Письмо пациенту и врачу отправляется после COMMIT. Пациент ограничен 3 переносами за 24 часа, регистратор — нет; не более одного события на визит. На старом томе CHECK `audit_events_change_values_check` пересоздаётся один раз при старте `migrate`.

Гость может зарегистрировать только `patient` на `/register`. Email приводится к нижнему регистру и уникален без учёта регистра. Помимо правил выше, пароль отклоняется, если после обрезки краёв он короче 8 символов, состоит из одного повторяющегося символа, совпадает с email/его локальной частью или входит в список типовых. Нужны полное имя (2–100 символов, без управляющих) и телефон (цифры, пробелы, `+()-`, не менее 5 цифр, до 40 символов). `register_patient` (`SECURITY DEFINER`) повторно проверяет данные и задаёт роль `patient`; у guest нет `INSERT` в `users`, сессия при регистрации не создаётся. Письмо подтверждения содержит одноразовую ссылку на 24 часа; `/verify-email` не показывает email, подтверждение требует POST с CSRF, затем вход — через `/login`. Неподтверждённый пользователь не входит (ответ как при неверном пароле; см. ниже). Форму повторной отправки ссылки `/login` показывает всегда; ответ единый, письмо — только неподтверждённому, старые ссылки аннулируются. Лимиты повторной отправки: 5 запросов за 15 минут на пару email+IP, 100 за 15 минут на IP, 10 в сутки на email. Forgot password доступен и неподтверждённым, подтверждает email и отзывает старые сессии. Служебные аккаунты создаются вне публичной формы и подтверждаются ссылкой установки пароля; demo-аккаунты уже подтверждены. Регистрация ограничена 20 попытками/15 мин и 100/сутки на источник, 5/сутки на email; превышение даёт HTTP 429 с `Retry-After`, одинаковый ответ для существующего и нового email, в таблице только хеши. Сбой БД даёт 503, неограниченная регистрация запрещена.

Имя и телефон хранятся в `patient_profiles` с CHECK и `FORCE ROW LEVEL SECURITY`: пациент видит/меняет свой профиль, регистратор видит профили пациентов, admin — только имя, врач — имя и телефон только своих пациентов через `SECURITY DEFINER`-функцию `doctor_visit_patients` (визиты за 12 месяцев, включая отменённые); guest не видит профили. В календарях/списках имя стоит перед email. Аудит `patient.profile.update` содержит только id. Демо-профили: `pat@clinic.local` — Narek Hakobyan, `pat2@clinic.local` — Ani Sargsyan; старые аккаунты получают заглушку, которую `/me` просит заменить. `/me` показывает до 3 ближайших будущих визитов пациента и ссылки на `/my` и `/my/records`. На странице врача пациент выбирает активную услугу до слота и видит длительность/буфер; после брони `/my` подтверждает врача, дату, время и услугу, показывает будущие визиты первыми, длительность, статус и отмену с подтверждением. Регистратор также видит детали успешной брони. Любая роль меняет свой пароль, указав текущий; `SECURITY DEFINER` проверяет роль и `auth_version`, приложению запрещён прямой UPDATE `users.password_hash`; аудит не содержит пароль или хеш.

Перед бронированием, отменой и переносом `data-confirm` показывает врача, услугу, дату и время (регистратору/admin — также имя пациента). Это только удобство: без JavaScript форма отправится без подтверждения; безопасность обеспечивают CSRF, RLS и серверные проверки. Jinja экранирует текст.

Для нового и занятого email `/register` одинаково отвечает 303 на `/login?registered=1` с «Check your email for the next step…» (email сравнивается без регистра, пробелы по краям удаляются). Новый адрес получает ссылку подтверждения; владелец занятого — письмо «Your clinic account» без имени и токена, со ссылками на вход и «Forgot password?». Аккаунт, пароль и токены не меняются; созданный посторонним неподтверждённый аккаунт владелец может забрать сбросом пароля. Сбой SMTP одинаков (`mail=failed`); лог — одна строка `could not send registration email (<класс ошибки>)`, без стека и адреса.

Неизвестный email, неверный пароль, заблокированная или неподтверждённая учётка получают одинаковый HTTP 401: «Invalid email or password. If you have just registered, confirm your email first.» Каждая попытка считается в лимите, счётчик не сбрасывается; `Account is blocked` показывается только при уже существовавшей сессии, отозванной блокировкой. Причина (`blocked`, `unverified` или `bad_credentials`) пишется только в `auth.login.failure`, без email.

Пациент может отменить/перенести визит не позже заданного срока: `/admin/settings` задаёт 0–48 часов (по умолчанию 2; 0 — до начала) через `set_patient_change_deadline_hours`, аудируемую как `clinic.change_deadline.update` со старым/новым значением. `public.patient_change_cutoff()` считает границу в `Asia/Yerevan`; RLS `appointments_patient_update` её проверяет независимо от `SET TimeZone`, поэтому прямой UPDATE внутри срока меняет 0 строк. На `/my` вместо кнопок показано «Online changes closed…»; попытка даёт `too_late` и предлагает позвонить. Регистратор/admin не ограничены сроком, но визит не должен начаться; новый слот переноса может быть внутри срока.

Непредвиденная ошибка `api` показывает 500 «Something went wrong» и 8-hex `ref` без деталей. `docker compose logs api` содержит тот же ref, метод, путь без query, класс исключения и stack trace. Если `api` недоступен, nginx показывает 502/504 из `docker/proxy/errors/clinic-unavailable.html` с теми же security headers.

На `/admin/doctors` admin создаёт врачей с аккаунтом, меняет имя/специальность/стаж и активирует или деактивирует их. Перед деактивацией показывается число будущих визитов; они остаются запланированы и требуют отдельного решения. Админ может блокировать других админов, но не себя; не задаёт пароли и не меняет email. Создание нового админа требует текущий пароль и аудируется (`admin.create_denied` или `admin.create` с автором). Новые врачи, регистраторы и админы получают ссылку установки пароля; существующим доступны `Send reset link`/`Forgot password?`; ссылку себе отправить нельзя. Последнему админу её отправляют на сервере: `docker compose exec api python send_reset_link.py admin@clinic.local`. Смена email доступна только владельцу и требует подтверждения старого и нового адресов; ссылка действует 15 минут, отправляется только по SMTP и не выводится в браузере. Логи API/proxy не записывают `token` на `/reset-password` и `/confirm-email`; при сбое SMTP `send_reset_link.py` печатает только `user_id`. `auth_version` отзывает старые сессии. У `app_admin` нет прав/политик на медицинские тексты (`FORCE ROW LEVEL SECURITY`); `session_secret` обязателен, не имеет значения по умолчанию и читается из Docker secret. Письма в dev доступны в Mailpit (`http://127.0.0.1:8025`). После брони/отмены пациент и врач получают письмо, только если включили уведомления в `/me`; в письме врач, услуга и время слота, без медтекста и номера записи. Парольные/email-письма отправляются всегда; ошибка SMTP не отменяет бронь/отмену. Для прод задайте `SMTP_HOST`, порт, `SMTP_STARTTLS` или `SMTP_SSL`, при необходимости `SMTP_USERNAME` и `secrets/smtp_password`, а также `PUBLIC_BASE_URL`. Публичная форма создаёт только пациентов. Адрес/телефон клиники и значения-заглушки «Educational stand»/«000-00-00» меняются в `/admin/settings` до реального использования.

На `/admin/services` задаются длительность, буфер и врачи для каждой услуги. Пациент/регистратор выбирает услугу на странице слотов врача. Слот хранит снимки `duration_minutes` и `buffer_minutes`: визит длится первое значение, врач резервируется на их сумму; буфер не мешает брони у другого врача. Изменения касаются только новых слотов; существующие интервалы не меняются. Нельзя отвязать врача с будущими визитами (сначала отменить их или оставить врача) или удалить использованную услугу — её можно деактивировать.

Границы RLS можно проверить командой `./tests/run_tests.sh tests/test_rls_boundary.py`: она проверяет `SELECT id, patient_user_id` в `appointments`, `visit_notes`, `prescriptions` для пациента, видимость врача, запрет регистраторам/admin читать `body` и запрет другим ролям читать аудит. Вывод сохраняется в `experiments/rls_boundary_output.txt`.

В `.env` храните только несекретные настройки. Пароли БД, ключ сессии и SMTP-пароль в `secrets/` монтируются в `/run/secrets/`. `scripts/init_secrets.sh` создаёт недостающие файлы, не перезаписывает существующие и удаляет устаревшие `.env`-строки `POSTGRES_PASSWORD`, `CLINIC_API_PASSWORD`, `SESSION_SECRET`, `SMTP_PASSWORD`. Если секреты уже были в `.env`, пересоздайте стек: `docker compose down -v && ./scripts/init_secrets.sh && docker compose up --build -d`. Подробнее — `docs/sec_doc.md`.

Права на файлы в `secrets/`: `600` для владельца плюс ACL на чтение только тому пользователю контейнера, который читает файл (`postgres_password` — uid 999, `clinic_api_password`, `session_secret`, `smtp_password`, `demo_password` — uid 10001; `audit_db_password` — uid 10002, пользователь `audit_anchor`; `migrate` работает от root и ACL не нужен). Fallback без `setfacl` или на ФС без ACL: если `init_secrets.sh` запущен от root, файл отдаётся этому uid (`chown`, права `400`); иначе файл остаётся `644` (кроме ключей медполей и `audit_anchor_key`: они остаются `600`), а скрипт печатает `warning` с командой `chmod 600 <файл> && sudo setfacl -m u:<uid>:r <файл>` (сначала `chmod`, потом `setfacl`, иначе ACL перестанет действовать). Файлы, которыми вы не владеете, скрипт не трогает (`note`). Ограничения: в rootless Docker uid контейнера отображается на subuid хоста, и ACL на `10001`/`999` не сработает; в Docker Desktop (macOS/Windows) права общих папок не применяются; `cp -r` и zip без сохранения ACL их теряют.

Интерфейс использует Bootstrap 5.3.8 CSS без JS/CDN; статика обслуживается `api`, кешируется по хэшу, HTML — `Cache-Control: no-store`. Шаблоны без inline JS/CSS, обработчиков `on...=`, `data:`-картинок и `|safe`; nginx ставит CSP без `unsafe-inline` и остальные security headers. Полная спецификация, хэши и проверки — `docs/sec_doc.md`, раздел 7.

Демо-аккаунты `admin`, `doc`, `doc2`, `pat`, `pat2`, `reg` @clinic.local используют только `secrets/demo_password`. Seed создаёт их лишь в пустой БД; существующая БД сохраняет старый пароль до пересоздания (команда выше). Детали — `docs/sec_doc.md`, раздел 4.

Медицинские тексты шифруются в `api` (AES-256-GCM); БД/дампы содержат привязанные к строке пакеты `fe2`, ключ доступен только `api`. Миграция и ротация ключей — `docs/sec_doc.md`, раздел 6.

При первом запуске `api` миграция `python -m migrate_medical_fields` шифрует старый открытый текст и привязывает `fe1` к строкам; пока миграция не прошла, текст остаётся в БД/дампе открытым. Ручной запуск: `docker compose exec api python -m migrate_medical_fields`.

Не заменяйте `field_encryption_key` напрямую: старые записи станут нечитаемыми. `./scripts/rotate_field_key.sh` сохраняет старый ключ и создаёт новый; для перешифрования выполните `docker compose exec api python -m migrate_medical_fields --reencrypt`, затем удалите старый ключ. Порядок действий — `docs/sec_doc.md`, раздел 6.

Mailpit: http://127.0.0.1:8025 (именно `127.0.0.1`, не `localhost`, см. HSTS ниже).

Сайт: https://localhost:8450 (стенды Fixer и Planera — 8452 и 8453). HTTP-порт 8080 только перенаправляет на HTTPS (308).

### HTTPS на стенде (`CLINIC_TLS_MODE=local`)

`make start` (через `scripts/init_secrets.sh`) выпускает свой CA с `nameConstraints` (только `localhost`, `127.0.0.1`, `::1`; `extendedKeyUsage=serverAuth`) и серверный лист на год. Браузер предупреждает о сертификате, пока вы не импортируете `secrets/tls/ca.crt` (по желанию). Ключ CA не покидает хост и в контейнеры не попадает. Тесты ходят по HTTPS с `SSL_CERT_FILE=secrets/tls/ca.crt` (Makefile и `tests/run_tests.sh` ставят его сами).

**HSTS** на стенде — 1 час (`CLINIC_HSTS_MAX_AGE=3600`). HSTS действует на все порты `localhost`, поэтому после захода на стенд браузер будет открывать по HTTPS и другие локальные сервисы на `localhost`: Mailpit открывайте только по `http://127.0.0.1:<порт>`. Для настоящего домена — `31536000`; `includeSubDomains` и `preload` мы не ставим, это только рекомендация (preload практически необратим).

По умолчанию proxy слушает все интерфейсы (`0.0.0.0`), но сертификат стенда выпущен только на `localhost`/`127.0.0.1`/`::1`: с другой машины браузер предупредит о сертификате, а редирект с HTTP ведёт на `PUBLIC_BASE_URL` (`localhost`). Для доступа по сети используйте режим `provided` с настоящим именем. Чтобы открыть стенд только на этой машине, добавьте в `.env` строку `CLINIC_PROXY_BIND=127.0.0.1` и выполните `docker compose up -d proxy`.

Сессионная cookie: `SESSION_HTTPS_ONLY=true` по умолчанию (флаг `Secure`); `api` не стартует, если `PUBLIC_BASE_URL` не `https://`.

### Прод: `CLINIC_TLS_MODE=provided`

Образец настроек — `.env.prod.example`. Полная цепочка сертификата кладётся в `secrets/tls/server.crt`, ключ — в `secrets/tls/server.key`; `init_secrets.sh` их только проверяет, проверка вручную — `make tls-check`. В `PUBLIC_BASE_URL` — имя (не IP-литерал), без порта и пути. Получение сертификата: ACME DNS-01 (рекомендация) или HTTP-01 через webroot (`CLINIC_ACME_WEBROOT=true` и `docker-compose.acme.yml`). Обновление — только через `scripts/tls_reload.sh NEW_KEY NEW_FULLCHAIN` (проверка, бэкап, запись в те же inode bind-mount, `nginx -t`, graceful reload, сверка serial), например как `--deploy-hook` certbot: `--deploy-hook 'cd /srv/clinic && scripts/tls_reload.sh "$RENEWED_LINEAGE/privkey.pem" "$RENEWED_LINEAGE/fullchain.pem"'`. OCSP не нужен (Let's Encrypt закрыл OCSP в 2025), stapling — опция для корпоративного CA.

### Журнал аудита: хеш-цепочка и якоря

- Журнал `audit_events` только дописывается: `UPDATE`, `DELETE` и `TRUNCATE` запрещены триггерами, в том числе суперпользователю (триггеры в режиме `ENABLE ALWAYS`). Внешнего ключа на `users` нет: удаление неподтверждённого приглашения пишет событие `user.invite_discarded`, история остаётся.
- Каждая строка получает `seq`, `prev_hash` и `row_hash` = SHA-256 от предыдущего хеша и канонической формы строки v1 (поля по порядку, `<длина>:<байты>`, NULL — `-`, время — микросекунды UTC). Голова цепочки — `audit_chain_head`. Строки, записанные до `genesis_at`, получили хеши задним числом и не гарантированы. Пропала голова при наличии строк — `migrate` не стартует (восстановление из бэкапа), новую цепочку поверх старых строк он не строит.
- Сервис `audit_anchor` (пользователь БД `clinic_auditor`, только `SELECT` журнала и головы) раз в `CLINIC_AUDIT_ANCHOR_INTERVAL` секунд (по умолчанию 60, допустимо 10–3600) проверяет цепочку от последнего якоря и, только если она цела, дописывает в `/anchors/<chain_id>.log` (том Docker `<проект>_audit_anchors`, см. ниже) якорь `seq` + хеш с HMAC-SHA256 (цепочка MAC по строкам). Ключ `secrets/audit_anchor_key` монтируется только в `audit_anchor`: права `600` + ACL на чтение uid 10002, либо от root `chown 10002` и `400`; если ни то, ни другое невозможно, ключ остаётся `600` с предупреждением (никогда не `644`) и `audit_anchor` не стартует, пока не получит доступ. Запись якорей и реестра идёт под `flock` на `/anchors/.lock`.
- Проверка: `make audit-verify` (`OK chain=… rows=… anchors=… last_anchor_age=…` или `BROKEN seq=… type=…`, код 1). `--strict` (`VERIFY_ARGS=--strict`) даёт код 3, если какая-то цепочка закрыта `forced` или `offline`. Код 2 и строка `ERROR cannot check: …` — «не проверено» (нет ключа или БД недоступна). Это тоже красный статус, а не «OK»: атакующий с доступом к БД (например, `REVOKE SELECT`) может превратить `BROKEN` (1) в 2.
- Полная проверка: `audit_anchor` при старте и затем раз в `CLINIC_AUDIT_FULL_CHECK_EVERY` секунд (по умолчанию 600, допустимо 60–86400) выполняет ту же проверку, что `make audit-verify` (вся цепочка от `seq` 1, реестр, триггеры), под тем же `flock` и в том же снимке БД, что и якорь. Так правка старых строк (до последнего якоря) видна не позже чем через 10 минут, без ручного `make audit-verify`. Результат цикл пишет в публичный файл статуса `/status/status.json` (том `audit_status`): только состояние `ok`/`broken`/`unchecked`, времена, `seq` и тип нарушения из белого списка, без путей, id цепочек, хешей и MAC. `--once`, `--retire` и `--health` этот файл не пишут; healthcheck `audit_anchor` не изменился.
- Плашка «Log integrity» — только на `/admin/audit` (только admin, ответ с `Cache-Control: no-store`). `api` читает `status.json` из того же тома только на чтение (`audit_status:/audit_status:ro`), строго по схеме, и сам решает цвет по своим `CLINIC_AUDIT_ANCHOR_INTERVAL` и `CLINIC_AUDIT_FULL_CHECK_EVERY` (из окружения `api`, не из файла):
  - **OK** (зелёная) — только если инкрементальная проверка цела, последняя полная проверка прошла, в реестре не было подмены цепочки, последняя проверка не старше `3·interval+60` с, полная — не старше `2·full_every+60` с, и ни одно время не в будущем больше чем на 60 с;
  - **BROKEN** (красная) — нарушение с его типом и `seq` (например `row_hash`, `chain_replaced`); после подмены цепочки (`switch` в реестре, в том числе после `make reset … RETIRE_FORCE=yes` без архивации якорей) плашка остаётся красной навсегда, как и `make audit-verify`;
  - **not checked** (серая) — нет файла, файл испорчен или не по схеме, время в будущем, статус устарел (`audit_anchor` остановлен или завис), нет БД, нет тома якорей, цепочка закрыта.
  Плашка — **индикатор, а не источник истины**: она живёт на том же хосте и показывает то, что записал `audit_anchor`. Источник истины — `make audit-verify` и копии якорей за пределами сервера. Времена на плашке — Asia/Yerevan.
- Просмотр журнала пишется в журнал: каждый `GET /admin/audit` — событие `audit.view` (актёр — admin, цель `audit_log`, `target_id` — битовая маска заданных фильтров: 1 `action`, 2 `actor_role`, 4 `actor`, 8 `target_type`, 16 `target_id`, 32 `from`, 64 `to`; `before_id` в маску не входит). Значения фильтров (email, id, даты) и их хеши не пишутся никогда; на странице журнала маска показана списком имён полей. Повтор той же маски тем же admin пишется снова только через 10 минут после записанного события (окно — константа `public.audit_view_window()`, `api` её не меняет), новый набор фильтров пишется всегда. Запись идёт функцией `public.record_audit_view` (`SECURITY DEFINER`, `EXECUTE` только у `app_admin`) в отдельной транзакции до чтения журнала; если записать не удалось, журнал не показывается (**fail closed**, страница ошибки 503).
- На свежем стенде, пока `audit_anchor` не записал первый якорь (до одного интервала после `make start` или `make reset`), `make audit-verify` печатает `BROKEN type=registry_missing … no registry and no anchors yet`: реестра ещё нет. Это нормально; через интервал проверка даёт `OK`. Если же файлы якорей есть, а `chains.log` нет, `registry_missing` — настоящая тревога.
- Если тома якорей нет (удалён) или он пуст, а в БД уже есть цепочка дальше genesis, `audit_anchor` при `make start`/`restart` не открывает новую цепочку молча: пишет `ERROR audit chain registry missing`, ничего не пишет в каталог, становится `unhealthy`, `make audit-verify` даёт `BROKEN type=registry_missing … the database holds chain=…` (rc 1). Выход — вернуть якоря в том или `make reset CONFIRM=yes RETIRE_FORCE=yes` (`forced no_registry@-`). На свежем стенде ложной тревоги нет: одноразовый `audit_prepare` пишет `open` до запуска `seed` и `api`.
- **Окно риска — до 60 с (один интервал):** правку журнала, сделанную суперпользователем БД после последнего якоря (отключить триггеры и пересчитать хеши), якорь не увидит, пока она не попадёт под следующий якорь — а следующий якорь уже не пишется, если цепочка не сходится с предыдущим. Правка строк до последнего якоря обнаруживается всегда (эксперимент E6: 20/20, `experiments/e6_report.md`). Окно можно сжать до 10 с через `CLINIC_AUDIT_ANCHOR_INTERVAL`. Честная модель угроз: суперпользователь БД может отключить триггеры и пересчитать цепочку — его ловят только якоря.
- Реестр цепочек `/anchors/chains.log` (`open`, `retire`, `switch`, тоже с HMAC): новая цепочка без закрытия старой — тревога `chain_replaced` (healthcheck красный, `verify_audit` — `BROKEN type=chain_replaced`). `make reset` и `make fclean` сначала останавливают `proxy` и `api` и закрывают цепочку (`anchor.py --retire`), поэтому плановый сброс тревоги не даёт. При сломанной цепочке сброс останавливается, ничего не удаляя, но `proxy` и `api` остаются остановленными — `make start` вернёт стенд. Том БД проверяется через `$(DOCKER) volume inspect`, где `DOCKER` — часть `COMPOSE` до слова `compose` (`sudo -n docker compose …` → `sudo -n docker`; можно задать `DOCKER=…` явно). Без проверки цепочки (`--retire --offline`) сброс идёт только если Docker ответил `no such volume`; любая другая ошибка (нет доступа к Docker, демон не запущен, sudo просит пароль) останавливает сброс, ничего не удаляя; осознанный сброс — `make reset CONFIRM=yes RETIRE_FORCE=yes` (в реестре `retire … forced`, `verify_audit` печатает `WARN`). После подмены цепочки (`chain_replaced`) `make reset`/`make fclean` тоже требуют `RETIRE_FORCE=yes CONFIRM=yes`: в реестре `retire … forced chain_replaced@-`, строка `switch` остаётся, и `verify_audit` по-прежнему даёт `BROKEN type=chain_replaced`. Если реестра нет (том якорей удалён, очищен или подменён), а в БД есть цепочка (`last_seq > 0`; на любом запущенном стенде это так — seed и события старта), сброс тоже отказывает (rc 2) без `RETIRE_FORCE=yes`; с ним в новом реестре остаётся `retire … forced no_registry@-`. Без тома БД (офлайн) закрывать нечего — сброс идёт как раньше.
- **Начать заново после расследования подмены** (только администратор хоста и только после разбора инцидента: снятых копий БД и якорей, выводов и решения): тревога `chain_replaced` в `verify_audit` держится, пока в реестре есть строка `switch`, и обычной командой не снимается — так задумано.
  1. Заархивируйте якоря (команда копирования из тома — в разделе «Якоря аудита в томе Docker»; копию можно положить и на внешнее хранилище, например WORM), затем `make stop`, `docker compose rm -f audit_anchor audit_prepare` и `docker volume rm <проект>_audit_anchors`. Архив — улика, он нужен для `verify_audit --anchors <копия>` и разбора.
  2. `make reset CONFIRM=yes RETIRE_FORCE=yes`: тома нет — make создаёт новый пустой том (владелец uid 10002, права `700`). Реестра в нём нет, а в БД цепочка есть, поэтому без `RETIRE_FORCE=yes` reset откажет (rc 2, `BROKEN type=registry_missing`, ничего не удалено). С `RETIRE_FORCE=yes` первой строкой нового `chains.log` пишется `retire <chain> … forced no_registry@-` — видимый след того, что старую цепочку закрыли без её реестра; затем БД пересоздаётся.
  3. `audit_anchor` открывает новую цепочку; через интервал `make audit-verify` печатает `WARN retire forced chain=<старая> break=no_registry@-` и `OK chain=<новая> …` (rc 0; с `--strict` — rc 3, пока эта строка в реестре).
  Том якорей reset/fclean проверяет строго (`anchor.py --check-dir` в одноразовом контейнере `audit_anchor`): `/anchors` должен принадлежать uid 10002, права ровно `700`, без POSIX ACL. Иначе make останавливается до закрытия цепочки и ничего не удаляет; `make start` (его `audit_prepare` выставляет владельца и права) и повторите.
  Без шага 1 `make reset … RETIRE_FORCE=yes` тоже пройдёт (в реестре `retire … forced chain_replaced@-`), но `verify_audit` останется красным — это и есть след инцидента.
- **Не выполняйте `git clean -fdx` (или `-X`) в рабочей копии** со старым каталогом `audit_anchors/` (до перехода на том): он в `.gitignore`, и такая очистка удалит старые якоря без следа.

#### Якоря аудита в томе Docker

- Якоря и реестр лежат во внешнем именованном томе проекта `<проект>_audit_anchors` (`fixer_audit_anchors`, `clinic_docker_audit_anchors` …; другое имя — `CLINIC_AUDIT_ANCHOR_VOLUME`). Папки на хосте нет, поэтому uid хоста, ACL и файловая система (WSL2 с проектом на `/mnt/c`, rootless Docker, Docker Desktop) на якоря не влияют.
- `make start` создаёт том, если его нет (`docker volume create --label clinic.audit=keep …`). Владельца (uid 10002) и права `700` выставляет `audit_prepare`: стартует от root только с `CHOWN`/`FOWNER`/`SETUID`/`SETGID`, меняет владельца и права корня тома (не рекурсивно) и сразу переходит на uid 10002 без привилегий (`setpriv`); затем `anchor.py --prepare` проверяет каталог (`--check-dir`) и при ошибке не пускает `seed` и `api`.
- Том внешний: `docker compose down -v`, `make reset` и `make fclean` его **не удаляют**. Удаляет только явный `docker volume rm <имя>` (или `docker volume prune -a` / сброс Docker Desktop) — перед этим сделайте копию.
- Копия якорей из тома в файл (стенд может работать):
  ```bash
  docker compose run --rm --no-deps -T --entrypoint python audit_anchor -c "import sys, tarfile; t = tarfile.open(fileobj=sys.stdout.buffer, mode='w|'); t.add('/anchors', arcname='.'); t.close()" > anchors-$(date +%Y%m%d-%H%M).tar
  ```
- **Переход со старой папки `./audit_anchors`** (стенды до этой версии; `make start` предупреждает, если видит её рядом с новым пустым томом): `docker compose stop audit_anchor`, затем скопировать файлы в том от uid 10002 и проверить `make audit-verify` (та же цепочка):
  ```bash
  tar -C audit_anchors --exclude=./.lock -cf - . | docker compose run --rm --no-deps -T --entrypoint python audit_anchor -c "import sys, tarfile; tarfile.open(fileobj=sys.stdin.buffer, mode='r|').extractall('/anchors', filter='data')"
  make start && make audit-verify
  ```
  Старую папку не удаляйте, пока `make audit-verify` не покажет ту же цепочку. Если пропустить копирование, `audit_anchor` даёт `registry_missing` (красный статус, новая цепочка молча не открывается).
- Триггеры журнала — в режиме `ENABLE ALWAYS`. После ручного `DISABLE` включайте только `ALTER TABLE … ENABLE ALWAYS TRIGGER …` (простой `ENABLE` даёт режим `O`, `verify_audit` сообщит `trigger_mode`, а `migrate` вернёт `A`). **Восстановление только данных:** `pg_restore --data-only --disable-triggers …`, затем `ENABLE ALWAYS TRIGGER` — без `--disable-triggers` триггер `zz_audit_chain` перепишет `seq`, хеши и `created_at`, и история будет испорчена.
- На одном хосте root получает и БД, и ключ, и файлы якорей; против него помогают только якоря за пределами хоста. Рекомендация для прода: cron или systemd-timer раз в 5–15 минут копирует `<chain_id>.log` и `chains.log` из тома якорей (команда копии — в разделе «Якоря аудита в томе Docker») в WORM-хранилище (S3 Object Lock в режиме compliance, удалённый append-only syslog или почтовый ящик), а `verify_audit --anchors <копия>` сверяет внешнюю копию с локальной. Ключ `audit_anchor_key` храните и офлайн: без него якоря не проверить.

## Demo via ngrok

Публичное демо локального стенда через туннель ngrok (только `CLINIC_TLS_MODE=local`).

1. Установите ngrok и один раз сохраните свой authtoken: `ngrok config add-authtoken <token>`. Токен хранится в конфиге ngrok (или в `NGROK_AUTHTOKEN`), в репозитории и `.env` его нет, и скрипт его не печатает.
2. В `.env` укажите зарезервированный домен: `NGROK_DOMAIN=outspoken-wiry-fabric.ngrok-free.dev` (он уже есть в `.env.example`).
3. `make ngrok` проверяет ngrok, authtoken и домен, запускает `make start` с `PUBLIC_BASE_URL=https://$NGROK_DOMAIN` и `CLINIC_PUBLIC_TUNNEL=1` через окружение (`.env` не меняется) и открывает туннель на HTTPS-порт стенда (`CLINIC_PROXY_TLS_PORT`) с проверкой сертификата по `secrets/tls/ca.crt`. Ссылки в письмах и 308 с HTTP ведут на адрес туннеля.
4. Ctrl+C закрывает туннель, стенд продолжает работать со ссылками на туннель. `make ngrok-off` перезапускает стенд с адресом из `.env` (localhost).

Не запускайте `ngrok http 8080`: HTTP-порт отвечает 308 и перенаправляет на `https://localhost:…`. Туннель должен вести на HTTPS-порт стенда.

Если Docker у вас работает только через `sudo`, обычный `sudo` сбрасывает `PUBLIC_BASE_URL` и `CLINIC_PUBLIC_TUNNEL`, и контейнеры остались бы на адресе из `.env`. Поэтому после `make start` скрипт сверяет адрес в контейнерах `api` и `proxy` с `https://$NGROK_DOMAIN` и при расхождении останавливается с ошибкой, не запуская ngrok. Запускайте Docker без `sudo` (группа `docker`) или сохраняйте окружение: `make ngrok COMPOSE="sudo -E docker compose"` (если sudoers запрещает `-E` — `sudo --preserve-env=PUBLIC_BASE_URL,CLINIC_PUBLIC_TUNNEL docker compose`).

При первом заходе ngrok показывает свою страницу-предупреждение, нажмите «Visit Site». За ngrok все посетители приходят с одного адреса, поэтому лимиты входа и регистрации по источнику общие для всех. Mailpit через туннель не открывается: открывайте его по `http://127.0.0.1:<порт Mailpit>`, не через `localhost` (на `localhost` браузер после HTTPS-стенда включает HSTS).

**Внимание:** пока туннель открыт, сайт доступен всем, у кого есть ссылка. Дополнительную защиту туннеля (пароль ngrok, OAuth, список IP) решено не ставить. Закрывайте туннель и выполняйте `make ngrok-off` сразу после демо.

### Рабочее время и генерация слотов

На `/admin/schedule` выберите врача и примените одинаковые часы к будням, выходным, всем семи дням или выбранным дням. Перед сохранением таблица показывает текущие значения.

Генерация слотов использует один диапазон для выбранных врачей (по умолчанию от сегодня до 14 дней вперёд). Для активных услуг каждого врача резервируется сумма длительности и буфера; интервал между слотами равен большему из этой суммы и минимального интервала рабочего времени. Страница предупреждает, если услуга не помещается в рабочее окно.
