Цели `make` (`make` или `make help` выводит список):

- `make start` — создаёт `.env` и `secrets/`, если их нет, собирает и запускает стек; данные БД сохраняются, повторный запуск ничего не удаляет.
- `make stop`, `make restart` — остановка и перезапуск контейнеров.
- `make clean` — удаляет контейнеры и сети Compose (`down`), данные БД сохраняются.
- `make logs`, `make ps` — логи всех сервисов (`logs -f`) и список контейнеров.
- `make test` — тесты против запущенного стека; адреса и проект меняются переменными `TEST_BASE` (по умолчанию `http://localhost:8080`), `TEST_MAILPIT` (`http://127.0.0.1:8025`), `TEST_PROJECT`, а также `PYTHON` и `PYTEST_ARGS`.

**`make reset` и `make fclean` удаляют БД.** `reset` выполняет `down -v` и затем `start`; `fclean` выполняет `down -v --rmi local --remove-orphans` только для этого Compose-проекта (`docker system prune` не вызывается). Обе цели сначала спрашивают подтверждение; `CONFIRM=yes` пропускает вопрос, без `yes` ничего не удаляется.

Все цели вызывают `$(COMPOSE)` (по умолчанию `docker compose`), поэтому другой проект можно указать так: `make start COMPOSE="docker compose -p planera"`.



FastAPI, PostgreSQL и Nginx.

API и `seed` подключаются к PostgreSQL ролью `clinic_api`; `POSTGRES_USER` используется только миграциями и администрированием. Одноразовый сервис `migrate` применяет схему, роли и RLS-политики до запуска API. Роли `app_guest`, `app_patient`, `app_doctor`, `app_registrar` и `app_admin` используются как контексты доступа.

Схему и RLS применяет `migrate` от имени владельца БД; сид использует `clinic_api` и ролевые контексты. При первом запуске фиксированный seed-администратор создаётся ограниченной `SECURITY DEFINER`-функцией, доступной только `clinic_api` и работающей лишь при пустой таблице `users`. Остальные демо-учётки создаёт такая же функция, но только для заранее заданных email; `clinic_api` не получает `INSERT` в `users`. Для защищённых запросов `db_as(user)` в транзакции задаёт `SET LOCAL ROLE app_*` (роль выбирается только из белого списка) и `app.user_id`. RLS защищает клинические таблицы `appointments`, `visit_notes` и `prescriptions`, а также ограничивает доступ врача к своим `slots`, `work_hours`, `time_off`, `holidays` и заявкам time off. Врач получает данные пациентов только через ограниченную функцию `doctor_patients()`, а не прямым чтением `users`; она включает пациентов со `scheduled` и `completed` записями за последние 12 месяцев. Для подписей в расписании и календаре используется отдельная `doctor_visit_patients()`, которая учитывает и `cancelled`, поэтому отменённые визиты остаются в расписании врача.

`clinic_api` может читать из `users` только несекретные колонки; прямое чтение `password_hash` запрещено. Вход проверяется функцией `SECURITY DEFINER`, которая сверяет пароль в PostgreSQL и возвращает только данные учётной записи. Версия `auth_version` хранится в подписанной сессии и в `users`; её увеличение после смены или сброса пароля аннулирует все старые сессии пользователя. Пароль, который задаёт сам пользователь, везде одинаковый: 8–72 символа, минимум 4 разных, буква и цифра, не email и не его локальная часть, не из короткого списка вроде `password` и `12345678`. Пробелы внутри пароля разрешены, по краям — нет, и пароль не обрезается молча. Email перед сохранением, входом, сбросом и поиском приводится к `strip()` + `lower()`; пробелы внутри адреса запрещены. При смене или сбросе уже существующего пароля новый не может совпасть со старым хешем. После смены уходит письмо без пароля и без ссылки.
Неудачный вход ограничен пятью попытками на пару «email + источник» за 15 минут и 100 попытками с одного источника за 15 минут; при превышении возвращается HTTP 429 с `Retry-After`. Источник передаётся доверенным reverse proxy, а в таблице попыток хранятся только хеши email и источника. Под Docker Desktop все клиенты видны как шлюз Docker, поэтому лимиты на источник фактически общие для всех (как у входа); на сервере за reverse proxy источник — настоящий адрес клиента. Для существующего и несуществующего email выполняется одна проверка `crypt()` с одинаковой стоимостью, чтобы время ответа не показывало, есть ли учётка. Заблокированная учётка при входе без сессии отвечает так же, как неверный пароль: HTTP 401 «Invalid email or password», попытка засчитывается в тот же лимит; «Account is blocked» показывается только тому, у кого уже была сессия, отозванная блокировкой. NUL-байты во вводимых текстах отклоняются до обращения к PostgreSQL.

`appointments.status` ограничен значениями `scheduled` и `cancelled`. RLS разрешает пациенту создавать запись только на свободный существующий слот и менять статус только с `scheduled` на `cancelled`; заблокированный пациент не проходит проверку. Проверка занятости слота не раскрывает пациенту чужие строки appointments.

Время слотов хранится как местное время клиники; база данных, API и соединения PostgreSQL настроены на `Asia/Yerevan`. Врач видит заметки и рецепты по своим `scheduled` и `cancelled` записям, но добавлять их можно только для `scheduled`. Каждая заметка и каждый рецепт хранятся отдельной строкой; текст ограничен 4000 символами на сервере (до шифрования), а в базе хранится только в зашифрованном виде. Пациент видит свои записи на `/my/records`, в том числе после отмены визита. `/admin/audit` показывает последние события бронирования, медицинских записей и административных изменений; журнал хранит только актёра, действие и идентификатор цели, но не текст заметок или рецептов.

Врач может открыть список своих пациентов на `/doctor/patients` и карточку пациента с историей визитов, заметками и рецептами. Список и карточка ограничены функцией `doctor_patients()` и политиками RLS; медицинские записи отображаются только в пределах действующих правил доступа.

Регистратор может просматривать все визиты выбранного дня и всей недели для всех врачей на `/registrar/appointments?day=YYYY-MM-DD&view=week`; фильтр `doctor_id=ID` ограничивает календарь выбранным врачом. Справочник `/registrar/patients` показывает имя, телефон, email, статус блокировки и количество будущих визитов, ищет по имени или email, и регистратор может исправить имя и телефон пациента; поиск на странице слотов выполняется через `/registrar/patients/search`. Регистратор не получает медицинские тексты, пароли или другие медицинские данные. Медицинские тексты и настройки графика регистратору недоступны. Врач видит только свой календарь на `/doctor/calendar?day=YYYY-MM-DD`: свободные слоты, занятые визиты и закрытия по выходным, отпуску или празднику, без действий бронирования или редактирования расписания. Отменённая запись больше не занимает слот календаря. Для обоих календарей доступны режимы `view=day|week`, навигация по дню или неделе и переход к сегодняшней дате. Неверные параметры даты и режима показывают сообщение и безопасно переключают календарь на текущий день. Врач может отправить запрос time off с датами и комментарием; только администратор может одобрить или отклонить его. Одобрение создаёт обычный период `time_off` и удаляет свободные слоты; существующие визиты остаются для ручной отмены администратором.

Администратор видит будущие записи на `/admin/schedule` и может отменить каждую по отдельности. Генерация слотов и отпуск на прошедшие даты отклоняются; диапазон генерации ограничен 90 календарными днями включительно. Регистратор не может отменять прошедшие визиты.

Фильтры и страницы (только GET, значения проверяются по белым спискам и строгим разбором, неверное значение игнорируется с предупреждением, без 500). `/doctors` — специальность и поиск по имени врача (`specialty`, `q`, до 100 символов, `ILIKE` с экранированием `%` и `_`). Слоты врача — окно дат `day=YYYY-MM-DD` и `view=week|day` (по умолчанию неделя с сегодняшнего дня; прошедшие слоты регистратор и админ видят, только выбрав прошедшую дату), у регистратора ещё `hide_taken=1`. `/my` — `status=upcoming|past|cancelled|all` (по умолчанию `upcoming`), `doctor_id` из врачей своих визитов, `from`/`to` (не больше 366 дней), по 20 на странице (`page` до 500); заметки и рецепты грузятся только для визитов страницы и с фильтром по пациенту. Календарь регистратора — ещё `status=all|active` и `service_id`, у будущих визитов кнопки Reschedule и Cancel. `/doctor/appointments` — `status` и страницы по 20. Журнал `/admin/audit` (только admin) — `action` (точное значение или группа вида `auth.`), `actor_role`, `actor` (точный email, без поиска по подстроке), `target_type`, `target_id` (находит и старый id перенесённого визита), `from`/`to`; страницы по 50 по ключу `before_id` («Next» и «Newest»), без OFFSET. Просмотр журнала в журнал не пишется.

Перенос записи: `/appointments/{id}/reschedule` — пациент для своей будущей `scheduled` записи, регистратор для любой будущей записи незаблокированного пациента; врач и админ не переносят (админ только отменяет). Новый слот — только тот же врач и та же услуга, будущий, свободный, не выходной и не отпуск; другой врач или услуга — через отмену и новую бронь. Запись с заметками или рецептами не переносится (`has_records`). Всё в одной транзакции под ролью пользователя: старый визит отменяется, затем проверяется и вставляется новый (RLS INSERT и `is_valid_free_slot` как при брони, новых грантов на `appointments` нет — `UPDATE` только `status`), затем DEFINER `record_appointment_reschedule` ещё раз сверяет пару и пишет одно событие `appointment.reschedule` (`target_id` и `new_value` — новый id, `old_value` — старый, без имён и email); любая ошибка откатывает всё. Письмо «Appointment rescheduled» пациенту и врачу уходит после COMMIT. CHECK `audit_events_change_values_check` на старом томе один раз пересоздаётся при старте `migrate`. Пациент — не больше 3 переносов за 24 часа (регистратор не ограничен); событие журнала пишется только в той же транзакции, что и сам перенос, и не больше одного на визит.

Гость может создать аккаунт только с ролью `patient` на `/register`. Email нормализуется к нижнему регистру и уникален без учёта регистра; пароль короче 8 символов после обрезки пробелов, из одного повторяющегося символа, совпадающий с email или его локальной частью, либо входящий в список типовых значений, отклоняется без создания пользователя. При регистрации обязательны полное имя (2–100 символов, без управляющих) и телефон (цифры, пробелы, `+()-`, минимум 5 цифр, до 40 символов). Учётку и профиль создаёт одна `SECURITY DEFINER`-функция `register_patient` (роль `patient` зашита в функции, данные проверяются ещё раз); у гостевой роли нет `INSERT` в `users`. Регистрация не создаёт сессию. Новый пациент получает письмо со ссылкой подтверждения (действует 24 часа, одноразовая); ссылка открывает `/verify-email` без email на странице, подтверждение — кнопкой (POST с CSRF), после него вход через `/login`. До подтверждения верный пароль даёт 403 «Please confirm your email before signing in.» без сессии; заблокированная неподтверждённая учётка получает обычный 401. Новую ссылку можно запросить с `/login`: ответ всегда один и тот же, письмо уходит только неподтверждённому пациенту, старые ссылки гаснут, лимиты — 5 запросов за 15 минут на email и IP, 100 на IP, 10 в сутки на email. Сброс пароля по «Forgot password?» доступен и неподтверждённой учётке и подтверждает почту, а старые сессии и пароль перестают действовать; так настоящий владелец адреса забирает учётку, созданную чужими руками. Служебные учётки подтверждаются ссылкой установки пароля. Демо-учётки создаются уже подтверждёнными; на стенде письма смотрите в Mailpit. Создание служебных ролей остаётся вне публичной формы. Регистрация ограничена: 20 попыток за 15 минут и 100 в сутки с одного источника, 5 в сутки на email; при превышении HTTP 429 с `Retry-After`, ответ одинаков для существующего и нового email; в таблице только хеши. При сбое базы — 503, регистрация без лимита не проходит.

Имя и телефон пациента хранятся в `patient_profiles` (CHECK в базе, `FORCE ROW LEVEL SECURITY`). Пациент видит и правит только свой профиль на `/me`, регистратор — профили пациентов, администратор видит только имя (без телефона), врач — имя и телефон только своих пациентов через `SECURITY DEFINER`-функцию `doctor_visit_patients` (то же правило, что для email: визиты за 12 месяцев, включая отменённые); гость профилей не видит. В календарях и списках имя показывается первым, email — вторым. Правка пишется в аудит как `patient.profile.update` только с id, без имени и телефона. Демо-пациенты: `pat@clinic.local` — Narek Hakobyan, `pat2@clinic.local` — Ani Sargsyan; у пациентов, созданных до этой таблицы, стоит заглушка, и `/me` просит её заменить. Кабинет пациента `/me` показывает до трёх ближайших будущих визитов только этого пациента и даёт ссылки на полную историю `/my` и медицинские записи `/my/records`. На странице врача пациент выбирает активную услугу до выбора слота и видит длительность услуги и буфер. После записи `/my` подтверждает врача, дату, время и услугу; список визитов показывает ближайшие будущие записи первыми, длительность, статус и кнопку отмены с подтверждением. Регистратору также показываются детали успешной записи. Любая роль может сменить собственный пароль, указав текущий; сервер применяет те же ограничения, что и регистрация, включая пароль, совпадающий с email. Проверка и обновление выполняются `SECURITY DEFINER`-функцией с учётом роли и `auth_version`, без права приложения менять `users.password_hash` напрямую. Смена фиксируется в аудите без записи пароля или его хеша.

Администратор управляет врачами на `/admin/doctors`: может создать врача с учётной записью, изменить имя/специальность/стаж или деактивировать и повторно активировать врача. Перед деактивацией показывается число будущих визитов; они остаются запланированными и требуют отдельного решения. Администратор может блокировать другого администратора, но не собственную учётную запись. Администратор не задаёт пароль и не меняет email. Новый администратор создаётся только после подтверждения паролем текущего администратора; отказ пишется в аудит как `admin.create_denied`, успех — как `admin.create` с автором. Новые регистраторы, администраторы и врачи получают ссылку для установки пароля; существующие учётные записи — только «Send reset link» или «Forgot password?». Себе ссылку отправить нельзя. Последний оставшийся администратор не получает ссылку через сайт; на сервере это делает `docker compose exec api python send_reset_link.py admin@clinic.local`. Смена email доступна только владельцу и требует подтверждения и старого, и нового адреса. Ссылка действует 15 минут, уходит только по SMTP и не показывается в браузере. Access-лог API и прокси для `/reset-password` и `/confirm-email` не сохраняет `token`; `send_reset_link.py` при сбое SMTP печатает только `user_id`, не ссылку. `auth_version` аннулирует старые сессии. Медицинский текст закрыт `FORCE ROW LEVEL SECURITY`: у `app_admin` нет прав и политики на `visit_notes` и `prescriptions`. Ключ сессии читается из Docker secret `secrets/session_secret` и не может быть дефолтным. Локально письма принимает Mailpit на http://127.0.0.1:8025. После успешной записи и после отмены письмо уходит пациенту и врачу, если у адресата включены почтовые уведомления в `/me`: врач, услуга и время берутся из слота, без медицинского текста и номера записи. Письма о пароле и смене email отправляются всегда. Сбой SMTP не отменяет уже созданную или уже отменённую запись. Для настоящего сервера задайте `SMTP_HOST`, порт, `SMTP_STARTTLS` или `SMTP_SSL`, при необходимости логин (`SMTP_USERNAME`) и пароль в `secrets/smtp_password`, а также `PUBLIC_BASE_URL`. Публичная форма по-прежнему создаёт только пациентов. Адрес и телефон клиники на главной странице изменяются в `/admin/settings`. Значения по умолчанию «Educational stand» и «000-00-00» — демо-данные учебного стенда, а не реальные контакты; замените их в `/admin/settings` перед реальным использованием.

Услуги управляются администратором на `/admin/services`: у каждой услуги задаются длительность и буфер после неё, а также список врачей, которые её оказывают. Пациент или регистратор выбирает услугу на странице слотов соответствующего врача. В слотах сохраняются снимки длительности и буфера: визит пациента длится только `duration_minutes`, а врач резервируется на `duration_minutes + buffer_minutes`; буфер не мешает записи пациента к другому врачу. Изменение услуги влияет только на новые слоты, существующие слоты и записи сохраняют прежние интервалы. Нельзя снять с услуги врача с будущими записями: сначала нужно отменить эти визиты или оставить врача привязанным. Использованную услугу нельзя удалить — её можно деактивировать.

Для повторения проверки «сломанный SELECT» без фильтра по пользователю запустите `./tests/run_tests.sh tests/test_rls_boundary.py`: тест проверяет `SELECT id, patient_user_id` для appointments, visit_notes и prescriptions под пациентом, границы видимости врача, запрет регистраторам и администраторам читать `body`, а также запрет неадминистративным ролям читать аудит. Фактический вывод сохраняется в `experiments/rls_boundary_output.txt`.

`.env` содержит только несекретные настройки. Пароли БД, ключ сессии и пароль SMTP лежат в `secrets/` (не коммитится) и попадают в контейнеры как Docker secrets в `/run/secrets/`. `scripts/init_secrets.sh` создаёт недостающие файлы, не перезаписывает существующие и удаляет из `.env` устаревшие строки `POSTGRES_PASSWORD`, `CLINIC_API_PASSWORD`, `SESSION_SECRET` и `SMTP_PASSWORD`. Если раньше пароли были в `.env`, после этого пересоздайте стек: `docker compose down -v && ./scripts/init_secrets.sh && docker compose up --build -d`. Подробнее: `docs/sec_doc.md`.

Права на файлы в `secrets/`: `600` для владельца плюс ACL на чтение только тому пользователю контейнера, который читает файл (`postgres_password` — uid 999, `clinic_api_password`, `session_secret`, `smtp_password`, `demo_password` — uid 10001; `migrate` работает от root и ACL не нужен). Fallback без `setfacl` или на ФС без ACL: если `init_secrets.sh` запущен от root, файл отдаётся этому uid (`chown`, права `400`); иначе файл остаётся `644`, а скрипт печатает `warning` с командой `chmod 600 <файл> && sudo setfacl -m u:<uid>:r <файл>` (сначала `chmod`, потом `setfacl`, иначе ACL перестанет действовать). Файлы, которыми вы не владеете, скрипт не трогает (`note`). Ограничения: в rootless Docker uid контейнера отображается на subuid хоста, и ACL на `10001`/`999` не сработает; в Docker Desktop (macOS/Windows) права общих папок не применяются; `cp -r` и zip без сохранения ACL их теряют.

Внешний вид и заголовки безопасности. Интерфейс собран на Bootstrap 5.3.8 (только CSS, без Bootstrap JS и без CDN): `app/static/vendor/bootstrap/bootstrap.min.css` плюс свои `app/static/app.css`, `app/static/app.js` и SVG-иконки в `app/static/img/`. Статику отдаёт `api` (`StaticFiles`, без листинга каталогов); в шаблонах ссылки вида `/static/app.css?v=<хэш>`, поэтому такие URL кешируются надолго, а HTML-страницы отдаются с `Cache-Control: no-store`. В шаблонах нет `style=`, `on...=`, встроенных `<script>`/`<style>` и `data:`-картинок; подтверждения — атрибут `data-confirm`. nginx ставит строгий `Content-Security-Policy` (без `unsafe-inline`) и остальные заголовки на все ответы. Версия и SHA-256 Bootstrap, политика и правила — в `docs/sec_doc.md`, раздел 8.

Пароль демо-учёток (`admin`, `doc`, `doc2`, `pat`, `pat2`, `reg` @clinic.local) берётся только из `secrets/demo_password`: `seed` читает его как Docker secret и падает с ошибкой, если файла нет или он пуст. `init_secrets.sh` генерирует этот файл, если его нет, и не перезаписывает существующий, поэтому свой начальный пароль можно положить туда заранее. Известного демо-пароля в репозитории больше нет. Seed создаёт учётки только в пустой базе, поэтому в уже существующей базе остаётся старый демо-пароль, пока её не пересоздать: `docker compose down -v && ./scripts/init_secrets.sh && docker compose up --build -d`.

Текст заметок (`visit_notes.body`) и рецептов (`prescriptions.body`) шифруется в `api` (AES-256-GCM, библиотека `cryptography`) до записи в базу и расшифровывается только при показе врачу или пациенту. В базе и в дампе лежит пакет `fe2:<key_id>:<nonce>:<шифротекст>:<тег>`, а не текст; база принимает в этих колонках только такие пакеты. Пакет привязан к своей записи: в проверку целостности входят таблица, id строки и id визита, поэтому пакет, скопированный в другую строку (даже той же таблицы), не расшифровывается — `api` показывает ошибку, а не чужой текст. Ключ — файл `secrets/field_encryption_key` в формате `<key_id>:<64 hex>`; его создаёт `init_secrets.sh` (только если файла нет, существующий не перезаписывает и значение не печатает). Ключ монтируется как Docker secret только в `api`; `db`, `migrate` и `seed` его не получают, в SQL он не передаётся. Права на файл `600` плюс ACL на чтение для пользователя api (uid 10001), то есть не world-readable. Если `setfacl` нет, выполните `sudo chown 10001:10001 secrets/field_encryption_key secrets/field_encryption_previous_keys` (права `600` останутся). Без ключа или с пустым/битым ключом `api` не стартует.

Существующий том со старыми заметками открытым текстом шифруется при старте `api`: перед uvicorn выполняется `python -m migrate_medical_fields`, который шифрует открытые строки, перешифровывает пакеты первой версии `fe1` (без привязки к строке) в привязанные `fe2`, уже привязанные не трогает и безопасен при повторном запуске. Пока `api` с ключом не запускался на этом томе, старый текст остаётся открытым в дампе. Вручную: `docker compose exec api python -m migrate_medical_fields`.

Смена ключа без потери старых записей: `./scripts/rotate_field_key.sh` переносит текущий ключ в `secrets/field_encryption_previous_keys` (он остаётся для чтения) и создаёт новый с новым `key_id` (`v1` → `v2`). Затем `docker compose up -d --force-recreate api`: новые записи шифруются новым ключом, старые читаются по своему `key_id`. По желанию перешифровать старые строки новым ключом: `docker compose exec api python -m migrate_medical_fields --reencrypt`. Старый ключ удаляйте из `field_encryption_previous_keys` только после этого. Просто заменить `field_encryption_key` нельзя: всё, что записано старым ключом, перестанет читаться. Подробнее: `docs/sec_doc.md`.
